# Phase 3.1 Plan 02: 순차 주장 방 DO·알람·서버 봇 배선 Summary

03.1-01 의 순수 규칙을 방 Durable Object 에 배선했다. 방장이 고르면 곧바로 모든 소켓이 다음 차례(`day.turn.seat`)와 공개 기록 한 줄(`day.claimLog`)을 받고 알람이 새 마감(호출 시각 + 8000)으로 옮겨지며, 나머지가 시간 초과하면 알람이 한 차례씩 `none` 으로 넘겨 마지막에 낮 토론이 된다. 서버 봇은 자기 차례에만 주장한다. 와이어 변경은 결정 0027 에 되돌리기 비용과 함께 기록했다. 트레이서의 서버 쪽이 여기서 닫힌다(화면은 03.1-03).

## 한 일

**Task 1 (트레이서)**: `worker/room.ts` 의 `applyClaim` 을 `selectClaim(this.room, playerId, claim, now)` → `tick(result.state, now, cryptoRandInt)` → `persistAndBroadcast()` → `reschedule()` 로 바꿨다. 옛 "마감이 바뀌지 않으니 reschedule 은 필요 없다" 주석과 `result.state === this.room` 비교를 지우고, claim 은 마감을 바꾼다(결정 0020 의 `pick` 과 다름)는 주석을 달었다. `test/worker/day.test.ts` 의 옛 직업 공개 묶음을 "차례 한 바퀴 (DAY-02)" 로 교체했다: claim 진입 view, 차례가 아닌 손님의 `WRONG_PHASE`(다른 소켓은 프레임 없음), 방장 claim 뒤 네 소켓의 다음 차례·`claimLog`·마감·`alarmOf`, 손님 선택과 시간 초과 알람 연쇄 뒤 낮 토론(자리 순서 네 줄), 2일차 시작 자리 이동(seat 1), claim 중 이모티콘 방송과 `say` 거부, 이미 지난 차례의 두 번째 claim, 서버 전용 키 부재. `alarm.test.ts` 는 claim 마감이 이전 마감 + 8000 으로 차례 수만큼 이어지는 표로, `testTools.test.ts` 는 claim 중 testSkip 한 차례씩 넘어가기·claim 도중 되돌리기 초기화 키 검사로 갱신했다.

**Task 2 (봇·전수 누출)**: `botClaimChoice` 가 맨 앞에서 `claim` 단계·생존·`currentClaimSeat` 를 검사해 난수 없이 `null` 을 돌려주고, `botPlanKey` 가 claim 에서 차례 번호를 더한 키를 낸다. 단위 테스트(호출 횟수 0, 차례인 봇 호출 순서 불변, 키·계획 전환)와 워커 테스트(방장 + 봇 3 이 한 명씩 주장해 낮 토론으로, 봇 차례 도중 testSkip 하면 낡은 계획이 버려지고 중복 claim 이 없음, 봇 차례 알람 = 봇 행동 시각)를 썼다. `leak.test.ts` 는 허용 경로에서 `.view.me.claim`·`.view.day.claims[].claim` 을 빼고 `.view.day.claimLog[].claim` 을 더했으며, 시나리오에서 1·2일차 차례인 사람이 실제로 한 번씩 고르게 하고, 모든 프레임의 모든 경로에서 `claimPick`·`claimOrder`·`claimIdx`·`claimStart` 키가 없고 `day.turn` 은 claim 단계 state 에만 있고 `claimLog` 줄의 키는 `n`·`seat`·`claim` 뿐임을 단언한다.

**Task 3 (결정 0027)**: 차례 규칙·와이어 변경·거부 코드 순서·봇·테스트 방 넘기기·주장 채팅 줄 방식·일지 와이어 열한 항목과 되돌리기 비용을 `docs/decisions/0027-sequential-claims-wire.md` 에 적었다. `docs/architecture.md` 는 직업 공개 시간·방식을 적은 줄이 없어(44행은 중립적) **변경 없음**이다.

## Deviations from Plan

### 계획대로 되지 않은 점 (의도는 유지)

**1. [참고] "이전 마감보다 앞당겨짐" 단언을 "원래 일정보다 앞섬"으로 정확히 옮겼다**
- 계획 문구는 방장이 고른 뒤 `phaseEndsAt` 이 이전 마감보다 앞당겨진다고 적었지만, 일찍 고르기의 새 마감은 `now + 8000` 이라 호출 시각이 지난 마감 이후이면 이전 마감보다 항상 뒤다. 실제 의미는 "다음 차례가 그 시점부터 8초를 받아 원래 일정(이전 마감 + 8000)보다 앞서 있다"이므로 `호출 시각 + 8000 ≤ 마감 ≤ 응답 시각 + 8000`, `마감 < 이전 마감 + 8000`, 저장된 마감 = `alarmOf` 로 단언했다. 단언은 느슨해지지 않았고 더 정확해졌다. 결정 0027-4 에도 같은 뜻으로 적었다.

**2. [참고] Task 1 RED 에서 일부 새 테스트가 이미 통과했다**
- claim 중 이모티콘·`say` 거부, 차례가 아닌 손님의 `WRONG_PHASE`, 2일차 시작 자리, testSkip 한 차례씩은 03.1-01 의 규칙이 이미 덮었다. 실제로 실패한 것(RED 증거)은 네 건: 방장 claim 뒤 다음 차례·알람 이동, 시간 초과 연쇄 뒤 낮 토론, 이미 지난 차례의 두 번째 claim, 서버 전용 키 부재 — 모두 옛 `applyClaim` 이 3인자 `selectClaim` 으로 마감을 `undefined` 로 만들고 tick·reschedule 을 부르지 않아 다음 차례 프레임이 오지 않는 실패다. Task 2 의 `leak.test.ts` 도 규칙이 이미 갖춰져 RED 에서는 통과했고, 허용 경로 변형으로 검사가 실제로 잡는지 확인했다.

**3. [Rule 3 - 막는 문제] 테스트 도우미를 새 계약에 맞췄다**
- `advanceTo` 반복 상한 12 → 40(계획 지시). `testTools.test.ts`·`bots.test.ts` 의 `skipUntil` 은 claim 이 같은 단계 state 를 여러 번 보내므로 "저장된 단계가 목표가 될 때까지, 보내기 전에 소켓 cursor 를 끝으로 옮기고 다음 state 하나를 기다린다" 로 바꿨고 쓰지 않게 된 `PHASE_ORDER` 를 지웠다.
