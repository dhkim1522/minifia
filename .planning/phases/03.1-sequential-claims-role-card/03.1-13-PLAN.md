이 계획은 서버 계약(03.1-01·02·04)을 배포 전에 소켓 수준에서 증명하는 **스크립트**를 새 규칙에 맞춘다. 스크립트는 지금 `claimReveal`·`claimDone`·`day.claims` 를 전제로 쓰여 있어 새 서버에서 모두 실패한다. 로컬 서버(`npm run dev`)에서 먼저 통과시키고, 배포본 실행은 03.1-14 이 한다.

## Claude 재량 결정

- **스크립트 각자 자기 안에 차례 응답 도우미를 둔다:** 스크립트들이 서로를 import 하지 않는 독립 파일이고(Windows 에서도 같은 명령, 외부 패키지 없음) 클라이언트 구조(`clients[]`, `frames`)가 조금씩 달라 공용 모듈을 만들지 않는다. 도우미는 "상태 프레임에서 `phase === "claim"` 이고 `day.turn.seat` 가 내 seat 이면 한 번 보낸다(키 = `${일차}:${seat}`)" 한 가지다.
- **차례 대기 시간을 한도에 넣는다:** claim 은 최대 인원 × 8초(8명 64초)다. 스모크 full 한도 300초 → 420초, uat-* 의 단계 대기 한도도 같은 만큼 늘린다. 일찍 고르는 클라이언트가 많으면 훨씬 짧다.
- **시간 초과 경로도 한 번은 건넌다:** 스모크는 한 클라이언트를 일부러 안 고르게 두어 8초 시간 초과(none)를 증명한다.
- **로컬 dev 서버 프로세스 규칙:** 이 계획이 띄운 프로세스만 다룬다. `npm run dev > "$LOG" 2>&1 & DEV_PID=$!` 로 띄워 PID 를 기록하고(셸이 호출 사이에 유지되지 않으면 임시 파일에 적는다), 끝날 때 `pkill -P $DEV_PID; kill $DEV_PID` 로 그 PID 와 자식만 끈다. 이름으로 찾아 죽이는 `pkill -f` 는 쓰지 않는다(다른 개발 서버를 건드릴 수 있다).
- **claim 단계 `firstState` 문제:** 옛 스크립트는 단계별 "첫 프레임" 을 찾는데 claim 은 차례마다 새 프레임이 온다. 필요한 곳은 `lastView`·조건식 대기(`waitUntil(() => … )`)로 바꾼다.
