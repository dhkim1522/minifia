## 반응 (Fast 4G · CPU 4×)

네트워크 프리셋 "Fast 4G" (사용자 확정 2026-10-31):

- 값: 다운로드 9 Mbps × 0.9 = 1,012,500 B/s, 업로드 1.5 Mbps × 0.9 = 168,750 B/s, 지연 60ms × 2.75 = **165ms** (CDP `Network.emulateNetworkConditions`, 바이트/초).
- 출처: Chrome DevTools 소스 `front_end/core/sdk/NetworkManager.ts` 의 `Fast4GConditions` (https://github.com/ChromeDevTools/devtools-frontend/blob/main/front_end/core/sdk/NetworkManager.ts, 2026-11-01 원문 확인). 같은 값이 `scripts/perf-run.mjs` 의 `FAST_4G` 상수와 결과 JSON `runner.network` 에 있다.

측정 방법: `node scripts/perf-run.mjs --mode interactive --throttle 4 --runs 3`. 회차마다 **새 컨텍스트(캐시·저장소 없음, 처음 방문)**에서 `/` 를 열어 제품 로비 경로로 [방 만들기] → 닉네임 [만들기] → 입장(`performance.mark("room-enter")`, Home.tsx) → 맵 조작 가능(`map-interactive`, `window.__mfWorld.interactiveMs()`). 이어 걸을 수 있는 점 하나를 눌러(손 뗌 시각 기준) `data-ring` 이 생길 때까지(링)와 내 `sample` 이 0.02 단위 움직일 때까지(출발)를 페이지 안 시계로 잰다. 끝에 방을 나가 지운다. 결과: `perf/interactive-dpr2-x4.json`, 스크린샷 `perf/interactive-dpr2-x4-run{1,2,3}.png`.

## 배포 직후 재접속 (deployhold)

**결과: 미확인(배포가 연결을 끊지 않았다). 원래 흐름은 돌릴 수 없었고, 축소한 탐침으로 갈음했다.**

1. `npm run e2e -- --only deployhold`(배포 전, 대상 = 당시 배포본 v2)를 먼저 돌렸으나 **setup 에서 실패**했다: `S4 단계 도달 — 맵이 열리지 않음 (훅 false, 상태 null, 이름표 0/2, 20초)`. 당시 배포본은 06-07 빌드(`2026-10-31T16:12:07Z+9a285ae`)로 맵 로비·`window.__mfWorld` 훅이 없어 deployhold 흐름의 설정(두 페이지가 맵에서 걷기)이 성립하지 않는다. 계획이 "배포본 = 지금 v2"라고 가정한 전제가 틀렸다. 이 실행 동안 배포는 하지 않았다.
2. 그래서 같은 배포본에 방장·손님 두 페이지를 로비로 붙여 두는 **축소 탐침**(저장소 밖 임시 스크립트, 맵 위치 이어짐 검사 없음)을 띄운 뒤 `npm run deploy` 를 **1회** 실행했다. 탐침은 배포 후 최대 6분 동안 두 페이지에 `.mf-reconnect` 띠가 뜨는지 보고, 끝에 인원·자리 일치, 마지막 소켓 열림, 콘솔 경고·오류를 본다. 원자료 `perf/deployhold-oldclient.json`.
3. 결과(배포 KST 12시 12분 무렵 → 6분 대기, 대기 시간 360,026ms):
   - 띠: 방장·손님 모두 **한 번도 뜨지 않음**. 두 페이지의 마지막 소켓은 계속 열려 있었다. 이 기간에 받은 state 프레임 0.
   - 인원·자리: 배포 전·후 `0:배포검사방장,1:배포검사손님` 로 동일, 단계 lobby 유지.
   - 콘솔: 앱이 낸 경고·오류 0(브라우저 자신의 v1.0 프리로드 미사용 경고 17개만, 06-18 `deferred-items.md` 의 허용 항목).
   - `/api/health` 버전: 배포 전 `…+9a285ae` → 배포 후 `…+350b7fb`.
4. 해석: 방 Durable Object 는 하이버네이션 API(`acceptWebSocket`, `worker/room.ts`)로 소켓을 받는다. 배포(코드 교체)가 열린 웹소켓을 끊지 않았고 6분 동안 띠 사이클이 생기지 않았다 — 이 조건에서 "배포 직후 띠가 떴다 사라진다" 는 계획의 기대는 관찰되지 않았다. 따라서 이 항목은 **통과도 실패도 아닌 미확인**이다(CONN-04 의 배포 경로 몫). 소켓이 실제로 끊기는 경우의 복구(띠·위치 이어짐·콘솔 0)는 06-18 reconnect 5종×10회(로컬)가 자동으로, 06-08 퇴거 복원 테스트가 서버 쪽으로 이미 덮고 있다.
5. 못 한 것: 새 클라이언트(맵 로비) 상태로 배포를 가로지르는 위치 이어짐 확인. 필요하면 지금 배포본(맵 로비 포함)에 두 페이지를 붙여 두고 사용자가 허락한 한 번 더의 배포(변경 없는 재배포 포함)에서 `npm run e2e -- --only deployhold` 를 돌리면 된다 — 이번 계획은 배포를 1회로 제한했다.
