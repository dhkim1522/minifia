# Pitfalls Research

**Domain:** 실시간 모바일 웹 마피아 게임에 "같은 공간"(걸어 다니는 공유 맵, 자유 채팅, 동작 캐릭터, 밤의 어둠, 유령, 사운드, 다시 하기)을 얹는 v2.0 마일스톤
**Researched:** 2026-10-30
**Confidence:** MEDIUM — 이 저장소 코드(`worker/room.ts`, `shared/game/view.ts`, `test/worker/leak.test.ts`, `wrangler.jsonc`)를 직접 읽고 판단한 항목은 HIGH 다. 플랫폼 동작(iOS Safari 소리·키보드·IME·WebGL, Cloudflare 한도)은 공식 문서와 웹 검색으로 확인했으나 gsd 출처 등급 기준으로는 LOW~MEDIUM 이다. 해당 페이즈를 시작할 때 실기기로 다시 확인한다고 적어 둔 항목이 그 표시다.

> 읽는 법: 이 문서의 "페이즈" 이름은 로드맵이 아직 없어 붙인 **임시 라벨**이다. 로드맵이 다르게 나뉘면 기능 기준으로 옮겨 읽는다.
> P0 프로토타입 게이트 · P1 v2 뼈대(배포·맵·이동·동기화) · P2 자유 채팅 · P3 캐릭터·의상·동작 · P4 지목→변론→찬반 · P5 밤·어둠·아침 · P6 유령·결과·다시 하기 · P7 사운드 · P8 안정성·v1 정리

## 먼저 알아 둘 구조적 사실 (v1.0 코드에서 읽은 것)

아래 네 가지가 이 문서 거의 모든 항목의 뿌리다.

1. **v1.0 은 "상태 전체를 사람마다 다시 만들어 보내는" 구조다.** `persistAndBroadcast()` 는 방 전체를 `storage.put("room")` 으로 저장하고, `broadcast()` 는 소켓마다 `buildView()` 를 새로 만들어 보낸다. 이 구조는 하루에 수십 번 바뀌는 투표·단계 전환에는 맞지만 초당 수 회 바뀌는 위치·입력 중 표시에는 맞지 않는다.
2. **v1.0 의 채팅은 "저장하지 않고 방송만" 한다**(결정 0017-7). v2.0 은 게임 끝에 마피아 밤 채팅과 유령 채팅을 공개해야 하므로 이 전제가 뒤집힌다.
3. **누출 검사는 이미 강하다.** `test/worker/leak.test.ts` 는 실제 소켓 프레임 전수 + 허용 경로 방식이다. 새 데이터(위치·채팅·유령)는 이 허용 목록에 **의도적으로** 들어가야 하고, 그 과정이 v2.0 의 가장 중요한 안전장치다. 반대로 허용 목록을 "테스트가 초록이 되도록" 넓히는 것이 가장 위험한 지름길이다.
4. **모든 메시지는 먼저 `advance()` 를 지난다**(만료 확인 + tick). 위치 메시지도 같은 길을 타므로 가볍게 만들지 않으면 방 전체가 느려진다. 방 Durable Object 는 단일 스레드이고 객체당 초당 약 1,000 요청이 소프트 한도다 [Cloudflare 한도 문서].

## Critical Pitfalls

### Pitfall 1: 위치를 "스트림"으로 설계해 v1.0 방송 구조에 그대로 태운다

**What goes wrong:**
클라이언트가 매 프레임 자기 좌표를 보내고 서버는 그때마다 `persistAndBroadcast()` 를 호출한다. 8명 × 초당 10~20회면 초당 수백 번의 전체 저장과 수천 번의 `buildView()` 가 돈다. CPU 와 저장소 쓰기가 폭증하고, 알람 처리(단계 마감)가 밀려 타이머가 늦게 넘어가며, 폰은 쏟아지는 전체 상태 프레임을 파싱하느라 발열한다. 또한 클라이언트가 보낸 좌표를 믿으면 마피아가 암살 대상 옆으로 순간이동할 수 있다.

**Why it happens:**
"실시간 이동 = 좌표 스트림"이라는 일반 멀티플레이어 습관, 그리고 v1.0 에서 잘 돌던 `persistAndBroadcast` 를 재사용하려는 자연스러운 선택.

**How to avoid:**
- **의도를 보낸다, 좌표를 보내지 않는다.** 이 게임은 터치 이동이다. 클라이언트는 "여기로 가겠다"(목적지) 한 번만 보내고, 서버가 걸을 길을 결정해 `{출발점, 출발시각, 경로, 속도}` 를 알려 준다. 모든 클라이언트는 그 식으로 현재 위치를 **계산**한다(서버 시각 기준). 걷는 동안 전송이 0 이다. 도착은 해석적으로 계산되므로 서버 틱 없이 기존 단일 알람(`reschedule()` 의 min 계산)에 도착 시각을 끼워 넣을 수 있다.
- 길찾기·충돌은 `shared/` 의 순수 TS(정수 격자 + 고정 순서 A*)로 두어 서버와 클라이언트가 같은 결과를 내게 한다. 부동소수점 갈림을 피하려고 격자 정수 + 틱 단위 시간을 쓴다.
- **위치는 `RoomState` 에 넣지 않는다.** 메모리 전용 채널로 두고 단계 경계와 "멈춤" 때만 저장한다(하이버네이션으로 메모리가 초기화되기 때문. 움직이는 동안은 메시지가 오가므로 깨어 있고, 가만히 있을 때 초기화될 수 있어 경계 저장이 필요하다). 소켓 첨부(`serializeAttachment`, 최대 16 KB)에 내 마지막 위치를 두는 것도 방법이다.
- 변경이 있을 때만 모아서 보낸다. Cloudflare 문서는 고빈도 데이터를 **50~100 ms 단위로 묶어** 보내라고 권한다. `setInterval` 은 하이버네이션을 막으므로 움직임이 없으면 반드시 끈다.
- 위치 갱신은 `state`(전체 뷰) 프레임과 **별도 프레임 종류**(예: `pos`)로 만든다. 와이어 계약은 v1.0 방식대로 결정 기록으로 먼저 적는다.

**Warning signs:**
`persistAndBroadcast` 호출 빈도가 이동 때문에 늘어난다 / 알람 기반 단계 전환이 1초 이상 늦는다 / 손으로 4탭 이상 열어 걷게 하면 폰이 뜨거워진다 / 서버 로그의 `room alarm failed` 가 늘어난다.

**Phase to address:**
P1(뼈대). 프레임 종류와 이동 모델을 정하기 전에 화면을 만들지 않는다.

### Pitfall 2: 밤 누출 — 내용만 막고 타이밍·크기·소리·재접속 경로를 놓친다

**What goes wrong:**
시민 편이 마피아의 위치를 알게 되는 경로는 "위치 데이터를 보냈다"만이 아니다.
- **타이밍:** 마피아가 움직일 때마다 전원에게 `state` 프레임이 가면, 내용이 같아도 "지금 누가 움직인다/행동했다"가 프레임 도착 시각으로 새어 나간다. v1.0 은 이미 이 문제를 알고 밤 행동 뒤 `state` 를 행위자에게만 보내도록 고쳤다(`sendViewTo`). 위치·입력 중 표시는 이 규칙을 다시 지켜야 한다.
- **소리:** 시민에게 들리는 발소리·심장 소리를 실제 마피아 이동이나 거리에 연동하면 소리 자체가 정보다. 연동하지 않고 "항상 같은 대본"으로 낸다 해도, 이벤트로 트리거하면 같은 문제다.
- **입력 중 "…":** 마피아 밤 채팅의 입력 중 알림이 낮 채팅과 같은 경로(전원 방송)를 타면 시민이 "누가 밤에 입력 중"을 본다. `nightChatRecipientIds` 가 채팅 이벤트에는 있지만 새로 생기는 이벤트 종류마다 같은 수신자 규칙을 붙이는 것을 잊기 쉽다.
- **재접속/하이버네이션 복구:** `hello` 로 새 소켓이 붙을 때 보내는 첫 스냅샷이 밤 필터를 거치지 않으면, 시민이 밤에 앱을 새로고침하는 것만으로 마피아 위치를 받는다.
- **클라이언트 캐시:** 낮에 받아 둔 "마지막 위치" 상태가 밤 화면에 남아 있다가 그대로 그려진다. 또는 시민 클라이언트가 위치 데이터를 받아 놓고 검은 덮개로 가린다(devtools 한 번이면 끝).
- **지연 노출:** 밤→아침 전환 프레임에 밤 중 이동 기록이 실려 온다.
- **판정 신호:** 암살이 "닿는 순간" 애니메이션·소리로 즉시 보이고 결과(죽음/의사 구출)가 거기에 인코딩되면 의사 판정이 새어 나간다. v1.0 에서 마피아의 `died` 비트는 아침에만 알려 주는 정책이었다.

**Why it happens:**
"화면에서 숨기기"가 가장 쉬운 구현이고, 내용 필터만 테스트하기 때문이다. 타이밍·크기 같은 부수 채널은 단위 테스트에 안 걸린다.

**How to avoid:**
- 시민용 밤 상태에는 **마피아 위치를 담는 필드 자체가 없다**(프로젝트 원칙: 숨기기가 아니라 보내지 않기). 시민 클라이언트는 밤에 맵 장면을 아예 만들지 않고, 경찰·의사가 쓰는 "어둠 속 얼굴 목록"은 초상 이미지 목록으로 만든다.
- 새 프레임 종류(`pos`, `typing`, `emote`, `chat`)를 만들 때마다 **수신자 함수 하나**(`recipientsOf(kind, sender, state)`)를 거치게 한다. 방송은 이 함수 결과에만 보낸다. 직접 `broadcastEvent` 를 부르는 코드를 새로 만들지 않는다.
- 시민 쪽 밤 프레임은 **마피아 활동과 무관한 일정**(단계 시작·마감)으로만 도착하게 한다.
- 긴장 연출 소리는 서버 이벤트와 무관한 클라이언트 로컬 대본(시작 시각과 단계 길이만 입력)으로 낸다.
- 재접속 스냅샷도 같은 `buildView`/`recipients` 경로를 쓰고, 밤 재접속 시나리오를 테스트에 넣는다.
- 단계가 바뀔 때 클라이언트의 위치·입력 중 캐시를 비운다.
- 암살 연출은 결과와 무관하게 같고, 피해자에게만 가는 "암살 이펙트"는 **밤 마감 판정 뒤**에 보낸다(Pitfall 11 참고).
- **새 검사: 메타모픽 누출 테스트.** 같은 시드로 판을 두 번 돌린다. 한 번은 마피아가 계속 움직이고 암살하며 채팅하고, 한 번은 가만히 있는다. 이때 **시민 소켓이 받은 프레임 열(종류·개수·크기·도착 순서)이 같아야** 한다. 기존 `leak.test.ts` 의 전수 허용 경로 검사에 위치·입력 중 경로를 의도적으로 추가하는 것과 함께 이 비교를 단계 완료 조건에 넣는다.

**Warning signs:**
시민 devtools Network 탭에서 마피아가 움직일 때만 프레임이 보인다 / 시민 화면에서 특정 소리가 마피아 행동과 함께 난다 / `leak.test.ts` 를 통과시키려고 허용 경로 목록을 늘리고 있다 / 밤에 새로고침하면 화면이 낮 맵을 잠깐 보여 준다.

**Phase to address:**
P1 에서 수신자 함수·프레임 종류를 설계하고, P5 에서 메타모픽 테스트와 소리·재접속 검증으로 닫는다. P6 의 유령(관전 예외)과 함께 한 번 더 점검한다.

### Pitfall 3: 서버 판정 없이 클라이언트 위치를 믿거나 반대로 지연 때문에 판정이 어긋난다

**What goes wrong:**
암살 사거리, "지목 집결 완료", 도착 판정 등이 클라이언트 좌표에 의존하면 조작이 가능하고(프로젝트 원칙 위반), 서버 판정만 있으면 폰의 낡은 위치와 어긋나 "분명 닿았는데 안 찔림"이 생긴다. 또 서로 다른 폰 시계로 걷기 보간을 하면 같은 캐릭터가 사람마다 다른 곳에 있다.

**Why it happens:**
이동 모델(Pitfall 1)을 정하기 전에 판정 규칙을 정하고, 클라이언트 시계를 섞어 쓰기 때문이다.

**How to avoid:**
- 모든 판정은 서버 계산 위치로만 한다. 암살 요구는 "대상 seat" 하나만 받고 서버가 사거리·시간(밤·1회)·상태(생존·마피아)를 검증한다(기존 `pick` 방식과 같은 패턴: 행동 종류를 보내지 않고 서버 저장 역할로 결정).
- 사거리에는 **관용 반경**을 둔다(보간 지연 100~150 ms 만큼). 화면에서 "닿았다"로 보이면 서버도 닿았다로 판정하도록 충분히 넉넉하게 하고, 거부 때는 이유 없이 조용히 무시하지 말고 한 번 알려 준다(v1.0 WR-02 "조용히 사라진 메시지"의 재발 방지).
- 시계 동기화는 기존 `ping/pong` 의 `serverNow` 로 오프셋(왕복 절반 보정)을 구해 쓴다. 클라이언트 보간은 약간 과거(약 100 ms) 시점을 그린다.
- **다툼 규칙을 요구사항에 미리 쓴다:** 마피아 둘이 서로 다른 대상에게 다가가면 누가 최종 대상인가, 마피아가 한 명 죽어 있으면, 암살 시도 직전에 대상이 이동하면. 이 규칙이 비어 있으면 구현이 임의로 정해 버린다.

**Warning signs:**
"찔렀는데 안 죽었다" 질문이 테스트에서 반복된다 / 서버 로그와 화면 좌표가 몇 칸씩 다르다 / 암살 규칙이 코드 안 주석에만 있다.

**Phase to address:**
P1(이동·시계), P5(암살 규칙·사거리).

### Pitfall 4: 자유 채팅 경로를 v1.0 의 "템플릿 채팅" 가정 위에 올린다

**What goes wrong:**
- v1.0 서버는 자유 텍스트를 받지 않는 구조다(`strictObject`, 템플릿 ID, 연결당 20/s + 플레이어당 2초 쿨다운). 쿨다운을 그대로 쓰면 자유 채팅에서는 말이 조용히 사라지고(WR-02 와 같은 증상), 쿨다운을 풀면 도배가 된다. 이동·입력 중·동작이 같은 20/s 창을 나눠 쓰면 정상 플레이에서 한도에 걸린다.
- 길이 제한을 UTF-16 길이나 바이트로 하면 한글·이모지(ZWJ)·조합형 자모에서 잘리거나 어긋난다. macOS 일부 경로의 NFD 자모가 섞이면 같은 글자가 다르게 보인다.
- 서버가 채널(낮/마피아/유령)을 **클라이언트가 보낸 값**으로 정하면 밤 마피아 채팅을 공개 채널로 보내는 조작이 가능하다. 서버가 채널을 자기 판단으로 정하면, 위상 경계에서 마피아가 입력해 둔 비밀 메시지가 **아침 공개 채널로 넓어져** 나간다(말이 새는 방향의 사고).
- 채팅 기록을 `RoomState` 단일 키에 계속 붙이면 매 저장이 점점 커진다. 저장 값 한 개 한도(SQLite 기반 약 2 MB, KV 기반 128 KiB)에 가까워진다.
- 유령 채팅·마피아 채팅 기록이 재접속·중도 합류 때 수신자 필터 없이 "기록 전체"로 나가면 누출이다.

**Why it happens:**
기존 채팅 코드에 붙여 확장하기 쉽고, 위상 경계의 지연·재시도 시나리오를 상상하지 않아서다.

**How to avoid:**
- 입력 검증은 서버에서 **그래핌 수**(`Intl.Segmenter`) 기준 상한 + NFC 정규화 + 제어문자·방향 제어 문자(U+202E 등)·과도한 결합 문자 제거로 한다. 클라이언트의 `maxlength` 는 UX 용일 뿐이다.
- **너그러운 대신 정확한 속도 제한:** 메시지 종류별 토큰 버킷(채팅 / 이동 / 입력 중 / 동작)을 따로 둔다. 거부되면 입력창에 "잠시 후 다시"가 보이고 입력 내용은 지우지 않는다.
- 클라이언트는 `{text, phaseSeq}` 만 보낸다. **채널은 서버가 보낸 사람의 현재 상태(생존·마피아·밤 여부)로 정한다.** 그리고 `phaseSeq` 가 서버 현재와 다르면 **넓은 채널로 폴백하지 않고 버린다**(밤 비밀 메시지가 낮 공개로 둔갑하지 않게). 클라이언트는 버려졌을 때 "단계가 바뀌어 보내지 못했어요"를 보여 준다.
- 채팅 기록은 `RoomState` 와 **분리된 추가 전용 저장**(별도 키 또는 SQLite 테이블)에 쌓는다. 채널 태그를 붙이고, 게임 끝 공개와 재접속 복구 때 수신자별로 필터한다. 방 만료·다시 하기 때 정리 규칙도 함께 정한다.
- React 는 기본 이스케이프를 하지만 `dangerouslySetInnerHTML`, 자동 링크(`javascript:` 스킴), 닉네임·메시지를 캔버스·텍스처 텍스트에 그릴 때의 글꼴 깨짐을 금지 목록에 올린다. 링크 자동 변환은 만들지 않는다(범위 밖).

**Warning signs:**
같은 문자열이 클라이언트 길이 제한과 서버 길이 제한에서 다르게 센다 / 입력창에 쓴 글이 "전송"하자 사라지고 아무 데도 안 나온다 / 방 상태 저장 크기가 판이 길수록 늘어난다.

**Phase to address:**
P2 (전체). 결과 화면 공개는 P6, 기록 저장 구조는 P2 에서 먼저 정한다.

### Pitfall 5: 한글 IME 조합 중 Enter/전송·"입력 중" 표시가 틀린다 (iOS·Android)

**What goes wrong:**
- Enter 로 전송하면 **마지막 음절이 빠지거나 중복**된다(조합 중인 글자가 아직 확정되지 않았는데 keydown 이 먼저 처리됨). Safari 는 `compositionend` 가 확정 Enter 의 `keydown` 보다 **먼저** 오는 알려진 순서 차이(WebKit 버그 165004)가 있어 `isComposing` 검사만으로 부족하다 [Chrome 가이드·Square 글, 웹 검색].
- Android 소프트 키보드는 거의 모든 `keydown` 이 `keyCode 229` 로 와서 어떤 키인지 알 수 없다. keydown 으로 "입력 중"을 판단하면 안 된다.
- 조합 중에 React 제어 입력의 `value` 를 프로그램으로 바꾸면(전송 후 비우기를 조합 도중에 하거나, 비동기 setState) 조합이 끊기거나 마지막 글자가 남는다.
- "입력 중" 이벤트를 매 입력마다 보내면 20/s 한도와 방송 비용을 먹고, "입력 끝" 이벤트가 유실되면(화면 꺼짐, 연결 끊김) 머리 위 "…" 가 영원히 남는다.

**Why it happens:**
데스크톱 영어 키보드 기준으로 만든 `onKeyDown` Enter 전송 핸들러를 그대로 쓰기 때문이다.

**How to avoid:**
- 입력창을 `<form>` + 단일 행 `input`(또는 `enterkeyhint="send"` 지정) 으로 만들고 **`onSubmit`** 으로 전송한다. 소프트 키보드의 "보내기" 키와 전송 버튼이 같은 경로가 된다. 데스크톱 Enter 처리가 꼭 필요하면 `isComposing || keyCode === 229 || (compositionend 직후 수 ms)` 세 조건을 모두 본다.
- 전송 시점에는 **DOM 의 현재 값**을 읽고, 비우기는 조합이 끝난 뒤(다음 이벤트 루프)에 한다.
- "입력 중"은 `input` 이벤트(조합 중 포함)에서만 파생한다. 클라이언트는 **최대 2~3초에 한 번** `typing` 을 보내고, 서버는 **수명 약 4초**의 휘발 상태로만 다룬다(저장 안 함, 만료되면 서버가 알려 줌). 전송·blur·단계 전환 때 끝 신호를 보내되 유실돼도 서버 만료로 정리된다.
- 입력 중 이벤트의 수신자는 해당 채널 수신자와 같다(Pitfall 2).
- 실기기 테스트 항목으로 고정: iPhone Safari·Samsung 키보드(Chrome)·카카오톡 인앱 브라우저에서 "안녕하세요" "ㅋㅋㅋ" 길게 입력→전송, 마지막 글자가 빠지거나 중복되는지.

**Warning signs:**
전송 뒤 입력창에 마지막 자모가 남는다 / 한 글자씩 두 번 전송된다 / 입력을 멈췄는데 "…" 가 남는다.

**Phase to address:**
P2. 실기기 검증이 페이즈 완료 조건이다(회고 교훈 2).

### Pitfall 6: 소프트 키보드가 올라오면 화면·카메라·캔버스가 무너진다

**What goes wrong:**
iOS Safari 는 키보드가 올라와도 **레이아웃 뷰포트 크기를 바꾸지 않고** 비주얼 뷰포트만 줄인다(`interactive-widget` 미지원). 그래서 `100vh`/`100dvh` 가 안 줄고, `position: fixed; bottom: 0` 채팅 막대는 키보드 아래로 숨거나 튀며, 입력창에 포커스할 때 브라우저가 페이지를 스크롤해 맵과 헤더가 위로 밀려 올라간다. `visualViewport` 이벤트는 키보드 애니메이션 끝에 늦게(최대 수백 ms) 온다는 보고가 있다 [웹 검색: WebKit 버그]. Android Chrome 은 기본이 "비주얼만 줄임" 이라 마찬가지로 고정 요소가 가려질 수 있다. 입력 글자 크기가 16px 미만이면 iOS 가 포커스 때 확대한다. 거기에 캔버스를 키보드 높이에 맞춰 매번 리사이즈하면 WebGL 이면 버퍼 재생성, 2D 면 재그리기가 키보드 애니메이션 내내 일어나고 카메라가 튄다.

세로 폰에서 키보드(약 300px)를 빼면 맵이 보이는 높이는 모자란다. 게다가 지목·변론 단계에서도 채팅이 필요하다(결정 0044-6).

**Why it happens:**
데스크톱·안드로이드 에뮬레이터에서는 정상이라 iOS 실기기에서야 발견되고, 채팅 UI 를 "하단 막대" 로만 설계해서다.

**How to avoid:**
- **P0 에서 하단 채팅창 + 키보드 열림 상태의 화면 시안을 실제 폰 크기(360×640, 390×664 등 기존 E2E 크기)로 먼저 본다.** 키보드가 열린 맵에서 내 캐릭터와 타이머가 보여야 한다.
- 루트는 `overflow:hidden` + 내부 스크롤만 허용하고, 채팅 막대 위치는 `visualViewport`(height, offsetTop) 값을 CSS 변수로 받아 정한다. 입력은 16px 이상.
- 캔버스 크기는 **키보드와 무관하게 고정**(초기 큰 뷰포트 기준)한다. 대신 카메라 오프셋만 "보이는 영역의 중심" 으로 옮겨 내 캐릭터가 키보드 위 보이는 영역에 오게 한다.
- 키보드가 열린 동안 지난 채팅 3~4줄을 입력창 위에 겹쳐 보여 주고, 닫히면 원래 채팅창으로 돌아온다.
- Android 에는 `interactive-widget=resizes-content` 메타를 쓸지 별도 판단한다(설정이 iOS 에는 소용없어 분기 로직이 필요하다).
- 카카오톡 인앱 브라우저(WKWebView/WebView) 동작은 Safari 와 다르다. 링크 공유가 주된 입장 경로이므로 이 환경을 필수 확인 대상으로 둔다(Pitfall 15).

**Warning signs:**
채팅 포커스 때 상단 UI 가 사라진다 / 키보드를 닫아도 화면이 원위치로 안 돌아온다 / 화면이 확대된 채 남는다 / 특정 기종에서 입력창이 키보드에 가려진다.

**Phase to address:**
P0(시안), P2(구현·실기기).

### Pitfall 7: 작은 세로 화면에서 "터치 이동 + 카메라 추적"이 터치 제스처와 싸운다

**What goes wrong:**
- 맵 위 탭이 브라우저 제스처와 충돌한다: 더블탭 확대, 핀치 확대, 길게 눌러 선택/호출 메뉴, 당겨서 새로고침, iOS 가장자리 스와이프 뒤로가기(화면 왼쪽 끝 터치).
- 화면 좌표 → 맵 좌표 변환이 카메라 위치·DPR·비주얼 뷰포트 오프셋을 빠뜨려 탭이 손가락 위치와 어긋난다.
- UI 겹침(채팅 막대, 동작 버튼, 타이머)이 탭을 가로채거나, 반대로 탭이 UI 를 통과해 캐릭터가 걷는다.
- 8명이 가운데 모이면 겹쳐서 누구를 가리키는지 알 수 없고, 작은 캐릭터를 손가락으로 정확히 누르기 어렵다.
- 카메라 추적이 낮은 fps 에서 떨리거나, 맵 가장자리에서 튄다. 맵이 "한 화면보다 조금 넓은" 정도라 카메라가 거의 안 움직여 멀미보다는 **부자연스러운 미세 끌림**이 문제다.
- 여러 사람이 "가운데로 집결"할 때 걸어서 모이게 하면 충돌·정체로 지목 15초 안에 못 모인다.

**Why it happens:**
데스크톱 마우스 클릭 기준으로 만들고, 한 화면 UI(v1.0)가 터치 영역을 다 소유하던 습관 때문이다.

**How to avoid:**
- 맵 표면에 `touch-action: none`(또는 `manipulation`), `user-select: none`, `-webkit-touch-callout: none`, `overscroll-behavior: none` 을 적용하고, 포인터 이벤트로 `pointerdown→pointerup` 거리·시간이 작을 때만 "탭"으로 인정한다.
- 좌표 변환은 하나의 함수(`screenToWorld`)에 모으고 단위 테스트한다. DPR·카메라·뷰포트 오프셋을 인자로 받는다.
- 캐릭터 선택은 **관대한 히트 반경**과 "가장 가까운 후보 스냅"을 쓰고, 지목 단계에서는 탭 가능한 캐릭터 목록(이름표 칩)을 보조로 둔다.
- **집결은 서버가 정한 슬롯**(원형 배치)에 텔레포트 또는 짧은 이동 연출로 한다. 걸어서 모이게 하지 않는다. 이동 중이던 사람은 단계 전환 시각에 서버가 경로를 끊고 슬롯으로 보낸다. 모든 클라이언트는 같은 서버 시각으로 같이 멈춘다.
- 카메라는 한 프레임 지연 보간과 맵 경계 클램프를 쓰고, 맵이 작아 카메라 여지가 적으면 일부 구간은 고정한다.
- 화면 가장자리(좌우 약 16px)는 탭을 받지 않는 안전 영역으로 둔다.

**Warning signs:**
탭할 때 화면이 확대/스크롤된다 / 같은 위치를 눌러도 기기마다 목적지가 다르다 / 지목 단계에서 8명이 서로 겹쳐 누구를 눌렀는지 모른다.

**Phase to address:**
P0(시안·조작 프로토타입), P1(이동·카메라), P4(집결·지목).

### Pitfall 8: 렌더링 엔진(3D three.js vs 2D)을 늦게, 근거 없이 정한다

**What goes wrong:**
엔진을 고르면 에셋 규격, 의상 교체 방식, 번들 크기, 히트 판정, 사운드, 테스트 방법이 모두 따라온다. 가장 바꾸기 비싼 결정인데도 "3D 가 멋있어 보여서" 먼저 고르고 나중에 저사양 안드로이드·구형 아이폰·인앱 브라우저에서 프레임이 안 나오거나 로딩이 길어 되돌린다. v1.0 의 결정 0008 과 프로젝트 제약("무거운 3D 는 어렵고 2D 캐릭터·애니메이션 범위는 문제없다")이 이미 같은 경고를 하고 있다.

**Why it happens:**
데모에서는 8명 캐릭터가 잘 돌지만 10분 연속 구동·열·메모리·낯선 기기는 데모로 확인되지 않는다. 솔로 개발이라 에셋 제작 부담이 늦게 드러난다.

**How to avoid:**
- **P0 에 엔진 스파이크를 둔다(고정 기간, 통과 기준을 미리 쓴다).** 8캐릭터 + 맵 + 의상 교체 + 동작 5개를 **30분 연속** 돌려 본다. 실기기 3종 이상(구형 iPhone, 저가 Android, 카카오톡 인앱 브라우저)에서 평균 fps, 최악 프레임, 메모리, 기기 온도, 첫 로딩 시간을 잰다. 기준(예: 저가 기기 30fps 이상, 링크를 열고 3초 안에 로비 상호작용, 총 전송량 일정 이하)을 못 맞추면 2D 로 간다.
- 의견: 이 프로젝트(6~10분 판, 링크 입장, 솔로 개발, AI 도구로 에셋 제작, 나중에 Capacitor 래핑)에서는 **2D 레이어 파츠 + 관절 애니메이션**이 위험이 가장 낮다. three.js 는 의상이 "3D 메시"가 되어 에셋 제작·최적화 부담이 크다. 어느 쪽이든 아래 Pitfall 9~10 을 통과해야 한다.
- 어느 쪽을 골라도 **게임 규칙 코드는 렌더러와 분리**한다(렌더러는 서버 상태와 계산 위치를 입력으로 받아 그리기만 한다). 그래야 엔진 교체 비용이 화면 쪽에 갇힌다.

**Warning signs:**
데모를 PC 에서만 본다 / "최적화는 나중에" 가 반복된다 / 첫 로딩 용량이 처음부터 수 MB 다 / 폰이 3분 후 뜨거워진다.

**Phase to address:**
P0 (게이트). 결과가 P3 에셋 규격과 P1 렌더링 구조를 정한다.

### Pitfall 9: three.js 를 쓴다면 — 흔한 구멍 목록

(엔진을 three.js 로 정했을 때만 적용. 요약은 SUMMARY 에 "조건부")

**What goes wrong / How to avoid (한 줄씩):**
- **스킨드 메시를 `.clone()` 하면 뼈대가 공유·깨진다.** `SkeletonUtils.clone()` 을 쓴다. 의상 파츠는 같은 `Skeleton` 에 `bind` 하는 별도 `SkinnedMesh` 로 만들고, 뼈 이름·계층·휴식 자세·스케일을 에셋 규격에 못 박는다.
- **`dispose()` 는 자동이 아니다.** 지오메트리·머티리얼·텍스처·렌더 타깃을 의상 교체와 화면 이동 때 직접 해제한다. 해제를 놓치면 로비에서 의상을 몇 번 갈아입는 것만으로 메모리가 늘어나 iOS 가 탭을 죽인다. 개발 중 `renderer.info.memory` 를 화면에 띄워 감시한다.
- **WebGL 컨텍스트는 화면 잠금·앱 전환 때 잃는다(특히 iOS).** 이 앱은 이미 재접속을 지원하므로 `webglcontextlost` 에서 `preventDefault()` 하고, `webglcontextrestored` 에서 GPU 자원을 다시 올리거나, **복구가 실패하면 `location.reload()`** 로 자기 자리로 돌아온다(토큰 재접속이 이미 있어 가장 값싼 안전망). `WEBGL_lose_context` 확장으로 강제 테스트한다. 검은 화면이 "컨텍스트 소실"인지 "밤의 어둠"인지 구분 못 하게 되므로 밤의 어둠에는 최소한의 UI(타이머 고리, 은은한 문구)가 보이게 한다.
- **컨텍스트 한도.** 화면마다 새 `<Canvas>`/렌더러를 만들면 "Too many active WebGL contexts" 경고와 함께 오래된 컨텍스트가 죽는다. React StrictMode 의 개발 중 이중 마운트도 같은 증상을 낸다. **캔버스 하나를 앱 수명 동안 유지**하고 장면만 교체한다.
- **텍스처 메모리는 압축 전 크기로 계산된다.** 2048×2048 RGBA 한 장이 약 16 MB(밉맵 포함 약 21 MB) 다. 캐릭터 8명 × 파츠 × 큰 텍스처는 금방 수백 MB 다. 파츠 텍스처는 512~1024, 아틀라스, 공유 머티리얼로 줄이고 필요하면 KTX2(디코더 wasm 추가 용량 있음)를 고려한다.
- **항상 켜진 렌더 루프의 발열.** `devicePixelRatio` 를 1.5~2 로 상한, 안티앨리어싱 끄기, 그림자 맵 대신 블롭 그림자, 라이트 최소화, 움직임이 없을 때 프레임 수 낮추기. 낮은 FPS 에서도 이동 판정이 흔들리지 않도록 시간은 서버 시각 기준.
- **레이캐스트로 스킨드 메시를 맞히지 않는다.** 보이지 않는 캡슐 히트 프록시나 화면 반경 판정을 쓴다.
- **번들·로딩.** three.js 코어 + GLTF 로더 + Draco/KTX2 디코더(wasm)를 합치면 첫 로딩이 크다. 링크로 입장하는 게임이므로 입장 화면(JS 최소) → 로비 진입 시 렌더러 지연 로딩 → 의상은 선택할 때 로딩 순서로 쪼갠다. `public/_headers` 의 `/assets/*` 불변 캐시 규칙은 이미 있으니 새 파일을 해시 이름으로 두면 두 번째 입장부터 무료다.
- **React 와 프레임 루프를 섞지 않는다.** 프레임마다 바뀌는 값(위치·애니메이션)을 React 상태로 올리지 않는다(ref 변이로).

**Phase to address:**
P0(스파이크에서 위 항목을 실측), P1·P3 구현. (엔진이 2D 로 결정되면 해당 없음. 다만 2D 캔버스/DOM 도 컨텍스트 복구가 필요 없는 대신 DPR·메모리·레이어 수 한도는 같은 방식으로 실측한다.)

### Pitfall 10: AI 도구로 만드는 캐릭터 에셋 — 규격 없이 만들면 의상 교체가 성립하지 않는다

**What goes wrong:**
AI 생성 이미지·메시는 매번 비율, 앵커 위치, 조명 방향, 해상도, 스타일이 다르다. "공통 몸체 + 의상 파츠(머리·옷·소품)" 는 **파츠가 몸체 앵커에 정확히 맞아야** 성립한다. 파츠 하나씩 만들 때마다 어긋나 수작업 보정이 파츠 수 × 동작 수로 곱해진다. 3D 라면 생성된 메시가 뼈대가 없거나 토폴로지가 나빠 쓸 수 없고(폴리곤 수십만, UV 엉망, 4K 텍스처), 동작(목 긋기, 손사래, 울기…)마다 애니메이션 클립이 필요하다. 동작 N개 × 몸체 하나는 괜찮지만 "파츠가 동작 중에 몸체를 찌르는" 문제(관통)는 파츠 × 동작 조합마다 확인해야 한다. 생성물의 상업적 이용 조건·저작권 지위도 도구마다 달라 출시 단계에서 문제가 될 수 있다. Mixamo 같은 자동 리깅은 휴머노이드만 되고 약관 확인이 필요하다.

**Why it happens:**
"일단 하나 만들어 보고" 시작해 규격을 사후에 만들기 때문이다. v1.0 에는 이미 `design/characters/ASSET_SPEC.md` 와 에셋 검사 테스트(`test/unit/assets.test.ts`) 패턴이 있는데 v2.0 에서 이를 그대로 확장하지 않으면 잊힌다.

**How to avoid:**
- **P0 에서 "몸체 1 + 파츠 슬롯 N + 동작 M" 의 상한을 못 박는다**(예: 슬롯 4개, 동작 8개). 조합 수가 아니라 파츠 수 × 동작 수를 산정해 에셋 제작 일정을 낸다. "동작 추가"가 요구사항에 계속 붙는 것이 범위 확장 경로다(Pitfall 16).
- 몸체 하나를 **사람이 확정**한 뒤(앵커 좌표표, 기준 자세, 해상도, 팔레트) 파츠는 그 기준에 맞춰 생성·보정한다. 몸체를 바꾸면 모든 파츠를 다시 만들어야 하므로 몸체 확정 전에는 파츠를 대량 생성하지 않는다.
- 에셋 검증 스크립트를 `npm test` 에 넣는다: 파일 크기 예산, 이미지 크기, 앵커/뼈 이름 존재, (3D 면) 삼각형 수·텍스처 크기, 파츠×동작 렌더 스냅샷(관통 확인). v1.0 의 `assets.test.ts` 방식을 확장한다.
- 에셋 출처·생성 도구·약관을 `design/characters/manifest.json` 에 기록한다(출시 마일스톤에서 한 번에 확인할 수 있게).
- 로비에서 의상 선택은 **서버에는 "어떤 의상 ID"만** 보내고 서버가 허용 목록(전체 의상 ID)으로 검증한다. 의상은 역할과 무관해야 하므로(결정 0044-8) 역할을 추정할 수 있는 의상 노출(예: 경찰 직업 의상이 실제 경찰에게만 지급)을 만들지 않는다.

**Warning signs:**
파츠마다 사람이 손으로 위치를 조금씩 옮기는 보정이 늘어난다 / 동작을 추가할수록 파츠 관통 신고가 늘어난다 / 에셋 폴더 크기가 첫 PR 마다 2배가 된다.

**Phase to address:**
P0(규격·상한 확정), P3(제작·검증).

### Pitfall 11: 암살·의사 구출·아침 공개를 실시간 연출로 만들며 판정 비밀이 새거나 규칙이 모호해진다

**What goes wrong:**
마피아가 걸어가서 "찌르는" 순간 즉시 연출·소리가 나고, 피해자가 그 순간 "암살 이펙트"를 받으면, 이후에 도착하는 의사의 보호 선택이 의미를 잃거나(판정이 이미 끝남) 반대로 "찔렸는데 살아남았다"가 피해자에게 먼저 노출된다. v1.0 의 밤 판정은 마감에 한 번 하는 구조였다. 또 마피아 쪽지(익명)·유언(피해자가 시민 편에서 쓰는 글)이 아침 공개 시점에 서버가 만든 것인지 클라이언트가 보낸 것인지 불명확하면 쪽지 작성자가 새거나 조작될 수 있다. 분필 윤곽이 "그날 낮 동안 남는" 상태가 다음 판정에 섞이면 위치 충돌이 생긴다.

**How to avoid:**
- 실시간으로 보이는 것은 **마피아의 행동(걷기, 찌르기 모션)** 뿐이고, 결과(죽음/구출)는 **밤 마감 판정 뒤**에만 확정·전달한다. 마피아에게도 `died` 는 아침에 알려 주는 v1.0 정책을 유지한다. 찌르기 모션·소리는 결과와 무관하게 같다.
- 피해자의 "암살 이펙트"는 판정이 죽음으로 확정된 뒤 피해자에게만, 밤이 끝나기 전에 보여야 하면 **마감을 앞당기지 말고** 그 시점까지 지연한다.
- 유언은 밤 동안 시민 편이 **미리** 써 두고(서버는 보관, 누가 쓴 것인지 알려 주지 않음) 피해자가 확정되면 그 사람의 것만 아침에 공개한다. 쪽지·유언 텍스트도 Pitfall 4 의 검증을 거친다.
- 분필 윤곽은 맵에 붙은 상태(위치·낮 동안 유지)로 서버가 보관하고, 다음 밤 시작 때 제거한다.

**Warning signs:**
의사 테스트 시나리오가 "마피아가 찌르기 전에 의사가 먼저 선택해야 한다" 로 쓰이고 있다 / 피해자 클라이언트가 마감 전에 죽음을 안다 / 쪽지 작성자 정보가 어떤 프레임에든 있다.

**Phase to address:**
P5.

### Pitfall 12: 다시 하기·방장 이양 경쟁 상태

**What goes wrong:**
- **다시 하기:** 결과 화면의 이탈·화면 꺼짐으로 이미 없는 사람이 새 판 멤버에 들어간다 / 여러 명이 동시에 누른다 / 이전 판의 늦은 메시지(채팅, 이동, 투표)가 새 판 상태에 적용된다 / 이전 판 결과·채팅·위치·의상이 다음 판 뷰에 남아 역할이 새거나 이전 판 마피아 채팅이 유령 채팅으로 흘러온다 / 방 만료 알람(`expiresAt`)이 다시 하기에서 갱신되지 않아 새 판 도중 방이 닫힌다.
- **방장 이양:** 방장 폰이 10초 잠겼다가 돌아오면 이미 이양돼 있고(깜빡임/이중 방장), 이양 전에 방장이 보낸 "시작" 메시지가 이양 후 도착해 처리된다 / 다시 하기·테스트 방 도구(testMode)가 방장 계정에 묶여 이양 때 사라지거나 엉뚱한 사람이 받는다 / 마지막 사람이 나갔는데 방이 남는다 / 방장이 "나가기" 한 것과 "끊긴 것"이 구분되지 않는다.

**Why it happens:**
Durable Object 가 단일 스레드라 서버 내부 동시성은 안전하지만, **클라이언트의 낡은 가정**(이전 판, 이전 방장)은 서버가 막아 주지 않는다.

**How to avoid:**
- 서버가 `epoch`(판 번호)와 `hostSeq`(방장 변경 번호)를 가지고, 클라이언트→서버의 모든 행동에 `epoch`를 싣는다. 다르면 거부하고 최신 뷰를 보낸다(기존 `WRONG_PHASE` 와 같은 방식).
- 다시 하기는 "**준비** 표시한 사람만" 새 판 멤버로 한다(결과 화면에서 누르면 준비, 일정 시간 안에 안 누르면 제외). 방장이 시작하면 준비 안 한 사람은 로비 밖(관전/제외)으로 둔다. 역할·결과·채팅 기록·위치는 초기화하되 **이전 판 채팅 기록은 공개 완료 후 폐기**한다.
- 방장 이양은 **유예(예: 끊긴 지 30~60초)** 후 결정적 후계자(연결된 사람 중 `joinSeq` 가장 작은 사람)로 한다. 클라이언트는 방장을 주장하지 않고 `hostId` 만 믿는다. 방장 전용 행동은 수신 시점의 `hostId` 로 검사한다.
- testMode·봇은 방 속성(방장 속성이 아님)으로 옮긴다.
- 다시 하기·이양 때 알람(`reschedule()`)과 `expiresAt` 갱신을 함께 처리하는 경로를 하나로 만들고 테스트한다.

**Warning signs:**
다시 하기 뒤 한 명의 화면에 이전 판 결과가 번쩍인다 / 이양 뒤 화면에 방장 표시가 두 명 / 새 판 도중 "방이 닫혔어요".

**Phase to address:**
P6(다시 하기), P8(방장 이양·이탈자). 둘 다 `epoch`/`hostSeq` 계약은 P1 에서 와이어에 넣어 둔다.

### Pitfall 13: v1.0 기능 제거가 3,094개 테스트와 E2E 를 "초록으로 속이게" 만든다

**What goes wrong:**
순차 직업 주장(`claim`), 빠른 메시지(`say`), 이모티콘(`emoji`), 처형 여부 투표(`execVote`)·후보 선택(`candidateVote`), 고정 테이블 장면을 없애면 `PhaseId`, `PHASE_DEFS`, `view.day` 필드, 스키마, 봇 로직, `nyquist-*` 테스트, 화면 E2E 시나리오가 연쇄로 컴파일 에러와 실패를 낸다. 압박 속에서 (a) 테스트를 새 동작에 맞게 통째로 고쳐 **누출 검사의 강도까지 같이 낮추거나**, (b) `skip` 으로 남겨 죽은 테스트가 쌓이거나, (c) 기능을 안 지우고 두어 코드가 두 게임을 동시에 담게 된다. 특히 **봇과 테스트 방 도구**(결정 0022·0024)는 4~8명 테스트를 혼자 하는 유일한 수단이라, 새 흐름(이동·채팅·지목·밤 암살)을 봇이 못 하면 개발 속도가 멈춘다.

그리고 **배포 대상 혼동**: `scripts/e2e/run.mjs`·`scripts/gallery.mjs`·`scripts/prod-url.txt` 는 v1.0 주소(`minifia.dhplay.workers.dev`)를 기본값으로 쥔다. `wrangler.jsonc` 의 `name` 은 아직 `minifia` 다. 이 상태로 `npm run deploy` 하면 **v1.0 배포본을 덮어쓴다**(결정 0043 은 v1.0 을 그대로 두기로 했다).

**How to avoid:**
- **P1 첫 작업으로 Worker 이름(`minifia-v2`), `prod-url.txt`, e2e/smoke/gallery 기본 주소, `check-account.mjs` 확인을 바꾸고 첫 배포를 한다.** 바꾸기 전에는 `npm run deploy` 를 못 쓰게 가드한다. 새 Worker 는 Durable Object `Room` 클래스 마이그레이션(`exports.Room`, sqlite)도 새로 가진다는 점을 확인한다.
- **교살자(strangler) 순서:** 새 와이어를 옆에 추가 → 새 흐름 완성 → 낡은 기능 일괄 삭제. 낡은 코드는 **전용 삭제 페이즈**(P8)에서 코드와 그것만 검사하던 테스트를 함께 지운다. `skip` 은 금지한다.
- 삭제 대상 표를 먼저 만든다(기능 → 코드 → 테스트 파일 → E2E 시나리오 → 결정 번호). 테스트 개수 변화는 결정 기록에 남긴다(감소는 정상, 사유 필요).
- **불변 목록:** `leak.test.ts`, 허용 경로 방식, `view.test.ts` 의 비노출 검사, 재접속·알람 테스트는 삭제 대상이 아니라 **확장 대상**이다. 허용 경로를 늘릴 때는 결정 기록에 이유를 쓴다.
- 봇은 각 페이즈에 "봇이 새 흐름을 한다"를 포함시킨다(이동 목적지 무작위, 채팅 몇 줄, 지목 무작위, 마피아 봇 암살). 안 하면 그 페이즈 검증은 사람 4명을 부르는 일이 된다.
- 단계가 많이 사라지면(`claim`, `candidateVote*`) 단계 매트릭스 테스트(`nyquist-02-phase-matrix`)가 새 단계표 기준으로 자동 생성되도록 바꿔 둔다.

**Warning signs:**
테스트를 고칠 때 허용 목록 상수를 편집하게 된다 / `describe.skip`/`it.skip` 이 보인다 / 봇이 새 단계에서 멈춘다 / e2e 가 v1.0 주소로 초록이 난다.

**Phase to address:**
P1(Worker 분리·가드), 각 페이즈(봇), P8(삭제).

### Pitfall 14: iOS 소리 — 잠금 해제, 무음 스위치, 중단, 백그라운드

**What goes wrong:**
- 소리는 사용자 제스처 뒤에만 시작된다. 아키텍처 문서는 "방 참가 버튼에서 오디오를 깨운다" 로 정리해 뒀지만 **재접속(새로고침, 앱 복귀)·링크 직접 입장**은 제스처 없이 화면이 열린다. 이후 소리가 영원히 안 나고 아무도 모른다.
- iPhone 무음(링) 스위치를 켜면 Web Audio 가 기본으로 **무음**이다. iOS 17 이후 `navigator.audioSession.type = "playback"` 으로 해결된다는 보고가 있지만, iOS 18 에서 일부 설정(transient 등)이 반대로 소리를 없애는 보고도 있어 버전별 확인이 필요하다 [웹 검색: WebKit 버그]. 구형 우회(무음 `<audio>` 요소 재생)는 잠금 화면 미디어 컨트롤이 노출되는 부작용이 있다.
- 전화·알림·화면 잠금으로 `AudioContext` 가 `suspended`/`interrupted` 가 된다. 복귀 시 `resume()` 을 제스처 안에서 다시 불러야 한다.
- 백그라운드 탭에서 타이머가 늦춰져 `setTimeout` 기반 효과음 순서가 어긋난다. BGM 이 화면 잠금 중에도 이어지면 이상하다.
- 효과음 `<audio>` 요소는 지연이 크다. 디코딩된 버퍼는 PCM 으로 커져(스테레오 30초 약 5 MB) 메모리를 먹는다. iOS Safari 에서 Ogg 형식 지원이 늦었으므로 m4a/mp3 를 쓴다.
- 소리를 **정보 전달에 필수**로 쓰면(무음·이어폰 없는 환경) 사용자는 손해를 본다. 긴장 연출은 "있으면 좋은 것"이어야 한다.
- 소리가 서버 이벤트에 반응하는 순간 Pitfall 2 의 누출 경로가 된다.

**How to avoid:**
- 소리 상태를 한 모듈(`audio.ts`)로 모은다: `unlocked`, `contextState`, `muted`. 제스처 없이 열린 화면(재접속)에는 눈에 띄는 "소리 켜기" 한 번 탭 배너를 보여 주고, 켠 상태는 저장한다. `visibilitychange`/`statechange` 마다 상태를 점검한다.
- `'audioSession' in navigator` 일 때만 `type = "playback"` 을 쓴다. 무음 스위치에서 소리가 안 나도 게임이 성립하게 설계한다.
- 이벤트별 소리 목록은 "받은 프레임을 근거로만 재생"이라는 원칙 하나로 묶는다(방송 프레임에서 파생되지 않는 소리는 로컬 대본 한 곳에서만).
- 화면 꺼짐 방지(Wake Lock)는 이미 `useWakeLock` 이 있다. 어두운 밤 30초 동안 터치가 없으면 iOS 자동 잠금과 겹칠 수 있고 Wake Lock 은 가시성 변경 때 해제되므로, 밤에 재획득 경로를 확인한다. 인앱 브라우저에서 Wake Lock 지원 여부는 별도 확인(Pitfall 15).

**Warning signs:**
재접속한 사용자만 "소리가 안 나요" / 무음 스위치를 켠 친구가 게임이 이상하다고 한다 / BGM 이 잠금 화면에서 계속 난다.

**Phase to address:**
P7. 잠금 해제 모듈 뼈대는 P1(참가 버튼)에서 심어 둔다.

### Pitfall 15: 링크 입장 환경(카카오톡 인앱 브라우저 등)을 Safari 로만 테스트한다

**What goes wrong:**
이 게임은 "링크 하나로" 모이므로 사용자는 메신저 인앱 브라우저로 처음 연다. 여기서는 WebGL 컨텍스트/메모리 한도, Wake Lock, `audioSession`, 키보드 동작, 백그라운드 종료가 Safari 앱과 다르고, 앱 전환 시 페이지가 더 빨리 죽는다. 개발자가 Safari/Chrome 만 쓰면 팀 실게임 테스트 때 처음 드러난다(v1.0 회고의 반복).

**How to avoid:**
P0 스파이크와 각 화면 페이즈의 실기기 체크표에 "카카오톡 인앱 브라우저(iOS/Android)에서 링크 열기→로비→이동→채팅→소리→앱 전환 복귀" 를 넣는다. 지원이 안 되는 기능은 감지해 우회하거나 "브라우저로 열기" 안내를 보여 준다. 이 항목의 구체 동작은 내가 일반 지식으로 쓴 부분이 크므로 실측이 근거가 되어야 한다(MEDIUM-LOW).

**Phase to address:**
P0, P1(첫 배포 직후), 이후 모든 화면 페이즈의 실기기 확인.

### Pitfall 16: 한 마일스톤에 모든 것을 넣은 범위 확장

**What goes wrong:**
결정 0044-15 는 모든 범위를 v2.0 한 마일스톤에 넣는다. v1.0 에서 이미 한 번 "10일 개발 뒤에야 출시가 어렵다는 판단"을 겪었다(회고 교훈 1). 맵·이동, 자유 채팅, 동작 캐릭터 에셋, 처형 흐름, 밤 어둠, 유령, 사운드, 다시 하기, 방장 이양이 모두 새로 쓰이고, 각각이 "한 가지만 더"를 부른다(동작 추가, 의상 추가, 맵 소품, 시상식 칭호, 효과음). 에셋 제작이 개발의 병목이 된다. 그리고 재미를 보기 전에 계속 쌓다가 끝에서 "재미없다" 를 처음 알게 된다.

**How to avoid:**
- **P0 은 코드가 아니라 "사람과 해 보는 짧은 테스트"** 다: 종이/클릭 시안 또는 가장 단순한 프로토타입(사각형 캐릭터가 걷고 채팅하고 지목)으로 4명이 한 판을 해 본다. 재미 가설("움직임·채팅·동작이 사교를 만든다")이 확인되기 전에 에셋을 대량 제작하지 않는다.
- **얇은 세로 슬라이스 순서**로 로드맵을 짠다: 1) 사각형 캐릭터 + 맵 + 이동 + 채팅 + 배포(P1~P2), 2) 지목→변론→찬반(P4), 3) 밤(P5)으로 "한 판이 끝까지 도는" 첫 지점을 빨리 만든 다음 4) 동작·의상(P3)과 사운드(P7) 같은 꾸밈 층을 얹는다. 기능 순서가 아니라 **한 판이 끝까지 도는 시점**을 앞당긴다. (핵심 가치가 "한 판을 끝까지 마치는 것"이므로 이것이 마일스톤 우선순위와 맞는다.)
- 각 페이즈에 **팀 플레이 확인 한 번**을 포함한다.
- 페이즈마다 "동작 몇 개, 의상 몇 벌" 같은 숫자를 상한으로 못 박고, 상한 초과 요청은 백로그로 간다. 정식 출시(상표, 스토어 심사)는 이미 범위 밖이다.
- 사운드는 마지막, 단 "소리 모듈 뼈대"는 P1 에서 미리 둔다.

**Warning signs:**
페이즈 계획이 "~ 및 ~ 및 ~" 로 길어진다 / 2주째 팀이 게임을 해 본 적이 없다 / 에셋 요청 목록이 줄지 않는다.

**Phase to address:**
로드맵 구조 자체(전 구간). 특히 P0.

## Moderate Pitfalls

### Pitfall A: 앞서 만든 연결 경고(WR-01~04)를 마지막으로 미룬다
**What goes wrong:** `.planning/DEFERRED-BUGS.md` 의 WR-01~04(연결 계층 경고)는 "2페이즈 전에 고치는 것이 좋음" 이라고 적혀 있었다. 위치·입력 중·채팅은 모두 연결 계층 위에서 도는데, 연결 계층이 불안정한 채 쌓으면 "이동이 가끔 멈춤" 같은 원인 불명 증상이 생긴다. 결정 0044-12 는 안정성을 마지막(P8)에 둔다.
**Prevention:** P1 시작 때 WR-01~04 를 읽고, 위치/채팅이 건드리는 것(재접속 중복 소켓, 낡은 소켓 교체, 메시지 유실 경로)만 먼저 고친다. 나머지는 P8.

### Pitfall B: 첫 로딩 용량과 입장 지연
**What goes wrong:** 링크를 열자마자 맵, 캐릭터 8종, 의상, 사운드를 모두 받으면 느린 모바일 회선에서 입장 이탈이 생긴다. 반대로 지연 로딩하면 게임 시작 직후 일부 폰만 캐릭터가 늦게 나타난다(깨진 형상, 빈칸).
**Prevention:** 입장 화면 번들 최소 → 로비에서 맵/내 캐릭터 → 필요한 의상만 로딩 순서로 쪼갠다. 로비에서 "준비됨" 신호(에셋 로딩 완료)를 서버가 참고하되 **시작을 막지 않는다**(제한 시간 뒤 대체 자리 표시 그림 사용). `/characters/*` 의 `max-age=86400` 와 같이 파일명이 해시가 아닌 에셋은 교체 지연이 있다는 기존 주석을 따라 새 에셋은 해시 이름 + `/assets/*` 불변 캐시 쪽으로 둔다.

### Pitfall C: 전체 상태 저장소 구조 — 방 상태 단일 키
**What goes wrong:** 방 전체를 한 키로 저장하는 v1.0 구조에 채팅 기록·분필 윤곽·유언·의상·위치를 모두 넣으면 저장 값이 커지고 매 변경마다 직렬화 비용이 늘어난다. 위치(휘발)와 규칙 상태(영속)와 기록(추가 전용)이 같은 길을 타면 안 된다.
**Prevention:** 세 층을 나눈다. 영속 규칙 상태(`room`), 추가 전용 기록(채팅·유언), 휘발 상태(위치·입력 중·동작). 휘발 상태는 하이버네이션 후 복구 규칙(Pitfall 1)을 명시한다.

### Pitfall D: 동작(이모트) 남발과 조작
**What goes wrong:** 동작은 "혼자 실행" 이지만 연타하면 화면을 가려 방해(킹받는 요소가 장난이 아니라 괴롭힘이 됨)가 되고 8명이 동시에 쓰면 프레임이 떨어진다. 동작 효과음이 겹치면 소음이다. 이동을 막는 단계에도 동작은 허용되므로(결정 0044-7) 지목 화면에서 동작이 투표 UI 를 가린다.
**Prevention:** 동작 쿨다운(서버가 강제, 예: 3초), 동시에 재생되는 동작 상한, 동작은 캐릭터 위 일정 영역 안에서만, 동작 소리는 같은 동작이 중복되면 한 번만. 동작 이벤트도 채널 수신자 함수를 거친다(밤에는 마피아끼리, 유령은 유령끼리).

### Pitfall E: 닉네임·의상으로 역할이 추정된다
**What goes wrong:** 의상은 역할과 무관해야 하는데(결정 0044-8) 직업 의상을 눌러 입는 재미가 "나는 경찰 옷 입었다 = 경찰이다" 를 거짓 신호로 쓰게 만든다. 그 자체는 기능이지만, 서버가 의상 목록과 역할 배정을 연결하면(예: 직업 의상 첫 선택자에게 그 역할 배정) 누출이다.
**Prevention:** 역할 배정은 의상과 완전히 독립(난수만). 의상은 `PublicPlayer` 의 공개 필드이므로 `view.test.ts` 의 허용 목록에 이유와 함께 추가한다.

### Pitfall F: 유령 가시성
**What goes wrong:** 유령이 산 사람 화면에 위치·동작·입력 중·채팅·소리·그림자로 나타나는 경로가 하나라도 있으면 안 된다. 암살당한 사람이 아침 이전에 유령이 되는지, 처형당한 사람은 언제부터 유령인지 시점이 모호하면 한 프레임 동안 산 사람 화면에 남는다. 유령 → 산 사람 소통이 우연히 열린다(예: 유령이 동작으로 산 사람에게 신호, 지목 가리키기 UI 에 유령이 참여). 유령은 관전 예외(전체 직업)를 받으므로 서버가 "누가 유령인가" 를 탈락 확정 시점에 한 번 정하고 이후 모든 수신자 함수가 그 값을 쓰게 한다.
**Prevention:** `isGhost(player, state)` 단일 함수. 유령 프레임은 유령 수신자에게만. 산 사람에게 가는 위치 스냅샷은 `alive` 로 필터. 처형 직후 유령 전환 시각을 정하고 같은 프레임에서 산 사람 뷰에서 제거. 유령 관련 `leak.test.ts` 시나리오를 추가한다(살아 있는 소켓이 유령의 위치/채팅/입력 중/동작을 한 번도 받지 않음).

### Pitfall G: 화면이 많이 바뀌는데 실기기 확인을 끝으로 몰아 둔다
**What goes wrong:** v1.0 은 4페이즈에서 35개의 갭 보완 계획이 나왔다. v2.0 은 새 화면이 더 많다(맵, 채팅, 의상 시트, 동작 목록, 시상식).
**Prevention:** 화면 페이즈마다 UI-SPEC 먼저(`/gsd-ui-phase`), 폰 폭 3종의 실기기 확인을 페이즈 완료 조건으로 넣는다(회고 교훈 2). 시안은 캔버스로 승인받고 `design/` 사본을 기준으로 구현한다.

### Pitfall H: 시각 시간 경쟁 — "과반이 누르면 일찍 끝냄"
**What goes wrong:** 낮 토론 90초에서 살아 있는 사람 과반이 "그만하기" 를 누르면 일찍 끝난다(결정 0044-13). 끊긴 사람이 "산 사람" 에 들어가는 기존 규칙(생존자 수에 포함)과 섞이면 과반 계산이 안 맞고, 마감 직전 클릭이 알람과 겹쳐 두 번 전환될 수 있다.
**Prevention:** 과반 계산은 `isAlive` + 연결 여부 정책을 한 함수로, 전환은 기존 `advance()`·단계 번호(`phaseSeq`) 멱등 경로만 쓴다.

## Minor Pitfalls

### Pitfall a: 닉네임·채팅이 이름표/말풍선 레이아웃을 깬다
**Prevention:** 한글 긴 닉네임, 이모지 조합, 방향 제어 문자를 이름표 렌더 테스트에 포함한다(`nickname.ts` 의 기존 검증을 재사용).

### Pitfall b: 안전 영역(노치/홈 인디케이터)과 가장자리 제스처
**Prevention:** `env(safe-area-inset-*)` 를 채팅 막대·동작 버튼에 적용하고 가장자리 탭 무시 영역을 둔다.

### Pitfall c: 햅틱/진동을 웹에서 만든다
**What goes wrong:** iOS Safari 는 Vibration API 가 안 된다. 사용자 메모리 방침도 "앱 전용 기능은 앱 전환 때"다.
**Prevention:** 진동은 이번 마일스톤에서 만들지 않는다. 시각·소리 연출만.

### Pitfall d: 다시 하기로 대기실 닉네임 중복·좌석 번호가 어긋난다
**Prevention:** 다시 하기 때 좌석을 새로 배정할지 유지할지 결정하고(고정 자리를 없앴으므로 `seat` 은 이제 맵 슬롯이 아니라 식별자임을 문서화) 기존 `seat` 기반 비공개 필드(`allies` 등) 해석이 어긋나지 않는지 확인한다.

### Pitfall e: 서버 시각 기준 연출 vs 폰 로컬 시계
**Prevention:** 연출 시작은 서버가 준 마감 시각 기준으로 계산한다(기존 원칙). 폰 시계로 `Date.now()` 를 직접 쓰지 않는다.

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| 위치를 `RoomState` 에 넣고 `persistAndBroadcast` 재사용 | 코드가 가장 적고 재접속 복구가 공짜 | 초당 수십 회 전체 저장·뷰 생성, 알람 지연, 발열 | 절대 안 됨. P0 프로토타입의 1회용 스파이크에서만 |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| Cloudflare Durable Object WebSocket | 고빈도 전송에 `setInterval` 을 계속 켬 → 하이버네이션 불가·요금 | 이벤트 기반 + 움직일 때만 50~100 ms 묶음 틱. 들어오는 WebSocket 메시지는 20개당 1요청으로 계산되지만 CPU 는 그대로 쓴다 |
| DO 하이버네이션 | 메모리 상태(위치, 입력 중)가 깨어날 때 사라지는 줄 모름 | 영속 층/휘발 층 분리, 소켓 첨부(16 KB 한도) 또는 경계 저장 |
| Cloudflare 정적 에셋 | 새 에셋을 해시 없는 이름으로 두면 교체가 최대 1일 지연(`_headers` 주석) | 해시 이름 + `/assets/*` 불변 캐시 |
| 별도 Worker `minifia-v2` | `name` 을 안 바꾸고 배포해 v1.0 덮어쓰기 | `wrangler.jsonc`·`prod-url.txt`·e2e 기본 주소·`check-account.mjs` 를 같은 커밋에서 변경 |
| iOS Safari 오디오 | 참가 버튼에서만 잠금 해제 | 재접속 경로에도 "소리 켜기" 배너, 중단 상태 복구 |
| iOS Safari 키보드 | `100dvh`/`position:fixed` 를 믿음 | `visualViewport` 기반 위치 + 고정 캔버스 + 카메라 오프셋 |
| WebGL(three.js) | 컨텍스트 소실을 무시 | `contextlost` 에서 `preventDefault`, 복구 실패 시 `location.reload()` |
| AI 생성 에셋 | 생성물을 바로 앱에 넣음 | 규격 검증 스크립트 + 출처·약관 기록(manifest) |
| zod 스키마 | `strictObject` 의 장점을 잃고 `passthrough` 로 채팅 필드를 확장 | 새 메시지도 `strictObject`, `text` 는 서버 정규화 후 사용 |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| 위치 스트림 + 전체 뷰 재생성 | 서버 CPU 폭증, 알람 지연, 발열 | 의도 기반 이동 + 별도 `pos` 프레임 + 묶음 전송 | 8명이 동시에 이동하는 로비·토론 |
| 매 입력마다 `typing` 전송 | 20/s 속도 제한 도달, 불필요한 방송 | 2~3초 간격 + 서버 4초 만료 | 한 명이 빠르게 입력해도 |
| 채팅 기록을 방 상태에 누적 | 저장 크기 증가, 저장 지연 | 추가 전용 별도 저장 | 긴 판(수백 줄) |
| 항상 켜진 렌더 루프 | 폰 발열·배터리·fps 저하 | DPR 상한, 유휴 시 프레임 낮춤, 불필요한 효과 제거 | 약 3~5분 연속 구동 후 저사양 기기 |
| 큰 텍스처를 파츠마다 | iOS 탭 종료, 컨텍스트 소실 | 512~1024, 아틀라스, 의상 교체 시 dispose | 8캐릭터 × 의상 여러 벌 |
| 키보드 애니메이션마다 캔버스 리사이즈 | 프레임 끊김, 카메라 튐 | 캔버스 고정 + 오프셋 이동 | 채팅 포커스 때마다 |
| 첫 로딩에 모든 에셋 | 입장 이탈, 느린 회선에서 빈 화면 | 단계별 지연 로딩, 로딩 진행 표시 | 링크를 처음 여는 순간 |
| 동작·이모트 동시 재생 | fps 하락, 소음 | 서버 쿨다운 + 동시 재생 상한 | 8명이 동시에 동작 |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| 시민에게 마피아 위치/입력 중/소리 이벤트를 보냄 | 밤 정보 누출(게임 붕괴) — 높음 | 수신자 함수 단일화 + 메타모픽 누출 테스트 |
| 유령 위치·채팅·동작이 산 사람에게 감 | 유령 규칙 붕괴 — 높음 | `isGhost` 단일 함수 + 누출 시나리오 |
| 클라이언트가 채널/발신자/좌표를 정함 | 비밀 채널 위조, 순간이동 암살 — 높음 | 서버가 채널·발신자·위치 결정 |
| 위상 경계에서 채팅이 더 넓은 채널로 | 마피아 비밀 메시지 공개 — 높음 | `phaseSeq` 불일치 시 폐기(확대 금지) |
| 재접속 스냅샷이 밤 필터를 건너뜀 | 새로고침으로 정보 획득 — 높음 | 첫 스냅샷도 같은 뷰 함수, 밤 재접속 테스트 |
| 채팅 도배·초대형 메시지 | 방 마비, 스토리지 증가 — 중간 | 종류별 토큰 버킷, 그래핌 상한, 기록 상한 |
| 방향 제어/제로폭 문자로 이름표·채팅 위조 | 다른 사람 사칭 — 중간 | 서버 정규화에서 제거 |
| 서버가 의상 ID 를 검증하지 않음 | 존재하지 않는 에셋 요청, 렌더 예외 (v1.0 WR-04 와 같은 유형) — 중간 | 허용 목록 검증, 클라이언트는 모르는 ID 에 기본 대체 |
| 다시 하기에서 이전 판 비공개 필드가 남음 | 새 판 역할 추정 — 높음 | 판 초기화를 하나의 함수로 + `epoch` |
| 방장 권한을 클라이언트가 주장 | 방 장악 — 중간 | 수신 시점 `hostId` 검사 |

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|

| 무음 스위치에서 소리 없음 | 연출 손실 | 소리에 의존하지 않는 설계 + 상태 표시 |

| 의상 변경이 게임 중 불가능한 이유가 불명 | 혼란 | "의상은 로비에서만 바꿔요" 안내 |
| 다시 하기에서 누가 참여하는지 불명 | 혼란 | 준비 표시 목록 |

## "Looks Done But Isn't" Checklist

- [ ] **이동:** PC 탭 여러 개에서만 확인 — 실제 iPhone/Android 와 카카오톡 인앱 브라우저에서 탭 정확도(좌표 변환), 제스처 충돌, 가장자리 탭 확인
- [ ] **이동 동기화:** 같은 시각에 두 폰이 같은 위치를 그리는지(서버 시각 오프셋) 확인, 단계 전환 때 이동 중이던 캐릭터가 같이 멈추는지
- [ ] **서버 판정:** 클라이언트가 좌표를 보내는 경로가 없고 사거리·밤·1회·생존이 서버에서만 검증되는지
- [ ] **채팅:** 한글 조합 중 전송에서 마지막 음절 누락/중복이 없는지(iOS Safari, Android Chrome, 삼성 키보드, 카카오톡 인앱)
- [ ] **채팅:** 단계 경계에서 마피아 밤 채팅이 낮 채팅으로 넓어지지 않는지(`phaseSeq`)
- [ ] **채팅:** 길이·도배·방향 제어 문자·NFD 자모 입력의 서버 검증과 거부 UX
- [ ] **키보드:** 360×640 / 390×664 에서 키보드를 연 채로 내 캐릭터와 타이머가 보이는지, 닫으면 원위치인지
- [ ] **입력 중 표시:** 연결 끊김·앱 전환 후에도 "…" 가 남지 않는지, 밤에 시민에게 가지 않는지
- [ ] **밤 누출:** 메타모픽 테스트(마피아가 움직일 때/안 움직일 때 시민 프레임 열 동일), 재접속 스냅샷, 소리, 입력 중, 캐시
- [ ] **유령:** 산 사람 소켓이 유령의 위치/채팅/입력 중/동작을 한 번도 받지 않는지, 유령 전환 시점의 한 프레임
- [ ] **암살/의사:** 결과가 마감 판정 뒤에만 노출되는지, 쪽지 작성자 비노출
- [ ] **소리:** 재접속 후 소리 켜기, 무음 스위치, 전화/알림 중단 후 복귀, 화면 잠금 시 BGM
- [ ] **WebGL(3D 시):** 컨텍스트 강제 소실 → 복구/리로드, 의상 교체 20회 뒤 메모리, 30분 구동 발열
- [ ] **에셋:** 파츠 × 동작 관통 스냅샷, 크기 예산, 출처 기록
- [ ] **다시 하기:** 동시 클릭, 이전 판 늦은 메시지, 이탈한 사람 제외, 방 만료 갱신, 이전 판 비공개 필드 삭제
- [ ] **방장 이양:** 폰 잠금 10초 후 복귀, 이양 전 보낸 시작 메시지, testMode 이전
- [ ] **배포:** `wrangler.jsonc` name/URL/e2e 기본 주소가 v2 인지, v1.0 배포본이 그대로인지(`/api/health` 버전 확인)
- [ ] **v1.0 제거:** `skip` 없음, 허용 경로 상수의 변경에 결정 기록, 봇이 새 흐름을 수행

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| 위치가 `RoomState` 에 들어가 방송 구조에 묶임 | HIGH | 휘발 채널 분리, 와이어 프레임 종류 추가, 클라이언트 보간 재작성(이동 모델이 바뀌면 화면 전체 영향) |
| 밤 누출 발견 | MEDIUM | 해당 프레임 수신자 함수로 이전, 메타모픽 테스트 추가. 이미 배포된 판은 되돌릴 수 없으므로 배포 전 발견이 중요 |
| IME 전송 버그 | LOW | form submit 으로 전환, 조합 가드 추가 |
