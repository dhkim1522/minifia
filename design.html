1요구사항

  1. 여러 명(4~8명)이 방 코드로 한 방에 들어와 각자 폰으로 함께 플레이할 수 있어야 한다.
  2. 캐릭터가 맵 위를 이동하고, 다른 사람의 이동이 실시간으로 보여야 한다.
  3. 투표와 밤 행동이 같은 순간에 들어와도 결과는 하나로 정해져야 한다.
  4. 역할과 밤 행동처럼 숨겨야 할 정보는 볼 수 없는 사람에게 전달되지 않아야 한다.
  5. 채팅은 공개 · 마피아 · 유령 채널로 나뉘고, 다시 접속해도 대화가 남아 있어야 한다.
  6. 연결이 끊겨도 게임은 멈추지 않고, 다시 접속하면 같은 자리로 돌아와야 한다.
  7. 단계 전환과 타이머는 서버 기준으로 진행되어야 한다.
  8. 혼자 운영할 수 있고, 사용자가 없는 동안 비용이 거의 들지 않아야 한다.

2기술 및 설계 결정

2.1방 상태 관리

방마다 Durable Object객체 하나가 요청을 도착 순서대로 처리하고, 저장소와 알람을 함께 가진다
일반 서버 + Redis인스턴스가 늘면 방 상태 동기화와 분산 락이 필요하고, 서버를 직접 운영해야 한다
Firebase 같은 실시간 서비스판정이 클라이언트와 별도 함수로 나뉘어 서버가 규칙을 강제하기 어렵다
방장 폰이 서버 역할 (P2P)방장 폰이 모든 역할을 알게 되어 게임이 성립하지 않는다
  • 채택 근거방의 상태와 판정이 한 객체에 있어 락 없이 처리 순서가 정해지고, 서버가 규칙을 강제하며, 서버를 운영할 필요가 없다.
  • 감수한 점Cloudflare에 종속된다. 객체가 한 리전에 있어 한국에서 왕복 약 155ms가 걸린다(8.1).

2.2정보 전달 방식

플레이어별 상태 생성 + 단일 전송 경로서버가 플레이어마다 볼 수 있는 정보만 담아 보내고, 받는 사람은 한 함수에서 정한다
전체 상태 전송 후 화면에서 숨김구현은 쉽지만 숨긴 정보가 네트워크에 그대로 실린다
역할별 채널 구독같은 판정 규칙이 여러 채널에 흩어져 일관성을 지키기 어렵다
  • 채택 근거숨겨야 할 정보가 네트워크로도 가지 않고, 정보 경계가 한 곳에 있어 테스트로 증명할 수 있다.
  • 감수한 점모든 메시지가 한 함수를 거쳐야 해 새 기능을 넣을 때 제약이 생긴다.

2.3채팅 보관

서버 보관 + 줄마다 받는 사람 기록보낼 때의 받는 사람을 8비트 마스크로 줄과 함께 저장한다
저장하지 않음가장 단순하지만 재접속하면 대화가 사라진다
브라우저에만 저장서버 기준의 비공개 규칙을 복원에 적용할 수 없다
조회할 때 역할로 거름조회 시점의 역할로 판단해 “탈락한 뒤부터 보인다” 같은 규칙이 어긋난다
  • 채택 근거재접속해도 대화가 남고, 복원되는 범위가 실시간 전송과 같다.
  • 감수한 점쓰기가 늘어 줄 단위 키와 채널별 보관 상한으로 묶었다.

2.4연결 끊김 처리

서버 타이머로 진행 + 토큰 재연결끊겨도 진행하고, 마감까지 못 낸 투표는 무효표로 처리한다
끊기면 전원 일시정지공정하지만 한 명이 판 전체를 붙잡는다
끊기면 탈락모바일에서 흔한 끊김에 과도한 불이익을 준다
  • 채택 근거판 길이가 예측 가능하고, 진행 기준이 서버에 있다.
  • 감수한 점자주 끊기는 사람은 불리하다.

3시스템 아키텍처

3.1구성도

  • 게임 규칙은 서버와 클라이언트가 같은 코드를 쓴다. 판정은 서버에서만 하고, 클라이언트는 표시와 이동 예측에만 쓴다.

3.2외부 의존성 · 통신 인프라

구성 요소역할
Cloudflare WorkersHTTP 라우팅, 방 생성 · 참가 API, 정적 파일 제공. 상태를 갖지 않는다
Durable Objects방 코드 이름으로 방마다 하나. 게임 상태, 판정, WebSocket 연결을 맡는다
Durable Object StorageSQLite 기반 키-값 저장소. 방마다 격리되며 room · world · chat 키를 둔다
Durable Object Alarm방마다 하나. 단계 마감과 방 만료를 처리한다
외부 DB · 큐 · 캐시없다. 상태와 저장이 방 객체 안에서 끝난다
통신방 생성 · 참가는 HTTP, 게임 중에는 WebSocket. 객체가 한 리전에 있어 한국 왕복 약 155ms

3.3동시성 모델

  • 한 객체 안에서는 요청이 하나씩 처리된다. 같은 순간 들어온 투표도 도착 순서대로 반영되어 락이 필요 없다.
  • 방끼리는 객체가 분리되어 서로 영향을 주지 않는다. 방이 늘면 객체 수가 늘어난다.
  • 대기 중에는 객체가 메모리에서 내려가도 WebSocket 연결은 유지되고(하이버네이션), 다시 깨어날 때 저장소에서 상태를 읽는다.

배포: npm run deploy 한 번으로 검사 · 빌드 · 배포, 배포 버전은 /api/health로 확인

5.1논리 모델 (ERD)

도식은 옆으로 밀어 볼 수 있습니다.

  • 방 하나가 모든 엔티티의 경계다. 다른 방과 관계를 맺지 않아 방 단위로 저장소를 격리할 수 있다.

5.3캐시 설계

데이터읽기쓰기
방 상태 (room)메모리 사본. 저장소는 객체가 깨어날 때만 읽는다바뀔 때마다 바로 저장 (write-through)
위치 (world)메모리 사본이동 후 2초 모아 저장 (write-behind). 나가기 · 단계 전환 · 알람 때는 즉시
채팅 (chat:*)메모리 사본줄을 추가할 때 바로 저장
속도 · 도배 제한 기록메모리만저장하지 않는다. 잃어도 제한이 한 번 느슨해질 뿐이다
  • 외부 캐시는 두지 않았다. 방마다 객체 하나만 쓰기를 하므로 메모리 사본이 곧 캐시이고, 무효화할 다른 사본이 없다.

7신뢰성 · 보안

항목방식
인증참가 때 발급한 토큰으로 WebSocket 첫 메시지에서 자리를 확인한다. 같은 토큰으로 다시 접속하면 이전 연결을 닫는다
입력 제한본문 · 메시지 1KB, 연결당 초당 20건, 모든 메시지 스키마 검증
권한단계 · 생존 · 역할을 확인한 뒤 처리한다. 행동의 종류는 서버에 저장된 역할로 정한다
정보 경계플레이어마다 볼 수 있는 상태만 만들고, 서버 전용 값은 어떤 메시지에도 싣지 않는다
멱등 처리메시지 · 알람 · 연결 모든 진입점이 마감 지난 단계를 먼저 처리한다
알람 복구처리 중 예외가 나면 1초 뒤로 다시 건다
상태 복원객체가 메모리에서 내려가도 저장소 키로 같은 상태와 같은 다음 채팅 번호를 복원한다

8이슈 및 해결

8.1 왕복 155ms 환경에서 이동 지연 제거

문제
캐릭터를 탭하면 잠깐 멈췄다가 움직이고, 방향을 바꾸면 앞으로 튀었다.
원인
서버 처리는 0~1ms, 한국 왕복은 약 155ms. 서버 응답으로만 그려서 왕복 동안 멈춰 있었다.
해결
  • 내 캐릭터만 서버와 같은 길찾기로 먼저 이동하고, 응답이 오면 150ms에 걸쳐 맞춘다.
  • 서버가 거절하면 서버 위치로 되돌린다.
결과
위치의 기준은 서버에 두고 체감 지연만 없앴다. 단일 리전을 택하며 감수한 지연에 대한 대응이다.

8.2 서버가 쉬었다 깨어날 때 단계 처리 누락

문제
알람이 늦거나 객체가 메모리에서 내려갔다 깨어나면 밀린 단계를 한 번에 따라잡는데, 아침 단계를 건너뛰면 위치가 돌아오지 않는 결함이 있었다.
원인
건너뛴 단계의 진입 처리가 빠졌다.
해결
  • 단계별 진입 처리를 표 하나로 모아 건너뛰어도 순서대로 한 번씩 실행한다.
  • 메시지 · 알람 · 연결 모든 진입점이 마감 지난 단계부터 처리한다.
  • 알람 처리 중 예외가 나면 1초 뒤로 다시 걸어 알람이 멈추지 않게 했다.
결과
늦은 알람, 객체 퇴거, 재접속 어느 경우에도 같은 상태가 된다. 강제 퇴거 후 복원 테스트로 확인한다.
