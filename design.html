미니피아 설계 문서

방 하나를 서버 객체 하나로, 보여도 되는 정보만 보내는 실시간 마피아 서버

4~8명이 각자 폰으로 한 방에 모여 10분 안에 끝내는 게임입니다. 마피아 게임은 “누가 무엇을 아는가”가 곧 규칙이라, 서버 설계의 중심은 판정의 일관성과 정보 경계였습니다.

DESIGN DECISIONS

설계 결정

결정마다 번호를 붙여 결정 기록으로 남겼어요. 여기서는 그중 서버의 골격을 이룬 네 가지를 소개해요.

결정 0002

방 하나를 Durable Object 하나로

문제
4~8명이 같은 방에서 동시에 투표하고, 밤 행동을 보내고, 타이머가 돌아요. 판정은 한 곳에서 순서대로 일어나야 해요.
선택
방마다 Durable Object를 하나 두고 WebSocket으로 연결해요. 규칙과 판정은 그 객체 안에서만 실행해요.
다른 선택지
  • 일반 서버 + Redis: 인스턴스가 여러 개가 되면 방 상태 동기화와 락이 필요하고, 서버 운영도 따로 해야 해요.
  • Firebase · Supabase 같은 실시간 서비스: 판정을 클라이언트나 별도 함수에 나눠 두게 돼서, 서버가 규칙을 강제하는 구조를 만들기 어려워요.
  • 방장 폰이 서버 역할(P2P): 방장 폰이 모든 역할을 알게 되어 마피아 게임이 성립하지 않아요.
결과
방 상태가 한 곳에 있어 동시 입력이 순서대로 처리되고 락이 필요 없어요. 정적 파일도 같은 곳에서 배포해요.
감수한 것
Cloudflare에 종속돼요. 객체가 한 리전에 있어서 한국에서는 왕복이 약 155ms였고, 이는 아래 문제 1의 원인이 됐어요.
결정 0020 · 0061

플레이어마다 다른 상태를 만들어 보내고, 전송 경로는 한 곳으로

문제
화면에서 숨기기만 하면 개발자 도구로 다른 사람의 역할이 보여요. 밤의 마피아 행동, 유령의 위치처럼 “받으면 안 되는 사람”이 있는 정보가 많아요.
선택
서버가 플레이어별로 볼 수 있는 상태만 골라 만들어요. 모든 이벤트의 받는 사람은 audience 함수 한 곳이 정하고, 전송은 deliver 한 길로만 나가요. 새 기능도 이 길을 지나야 해요.
다른 선택지
  • 전체 상태를 모두에게 보내고 클라이언트에서 가리기: 구현은 쉽지만 네트워크에 정보가 그대로 실려요.
  • 역할별 채널로 나눠 구독: 같은 판정 규칙이 여러 채널에 흩어져 일관성을 지키기 어려워요.
결과
시민의 소켓에는 마피아의 행동이 한 프레임도 가지 않고, 산 사람의 소켓에는 유령의 위치와 채팅이 가지 않아요. 규칙이 한 곳에 있어서 테스트로 증명할 수 있어요(문제 3).
감수한 것
모든 프레임이 한 함수를 지나야 해서 새 메시지 종류를 더할 때 제약이 생겨요. 방이 4~8명이라 플레이어별 상태 계산 비용은 문제가 되지 않았어요.
결정 0058

채팅은 서버가 보관하고, 줄마다 받는 사람을 함께 저장

문제
새로 고침이나 재접속 뒤에도 채팅이 돌아와야 해요. 그런데 밤의 마피아 채팅과 유령 채팅은 비공개라, 복원이 실시간 전송보다 넓게 보여주면 안 돼요.
선택
줄 단위로 저장하면서 그 줄을 받은 사람의 좌석을 8비트 마스크로 같이 저장해요. 복원은 내 좌석 비트가 켜진 줄만 돌려줘요. 줄 번호는 채널마다 따로 세요.
다른 선택지
  • 저장하지 않기: 가장 단순하지만 재접속하면 대화가 사라져요.
  • 브라우저에만 저장: 서버가 보낸 줄만 남아서, 서버가 기준인 비공개 규칙을 복원에 적용할 수 없어요.
  • 전부 저장하고 조회할 때 역할로 거르기: 조회 시점의 역할로 판단하면 “탈락한 뒤부터 보인다” 같은 시점 규칙이 틀어져요.
결과
복원도 실시간 전송과 같은 규칙을 따라요. 번호를 채널마다 세는 이유는, 전체 번호를 쓰면 공개 채팅 번호의 빈틈으로 비공개 채널에 몇 줄이 오갔는지 알 수 있기 때문이에요.
감수한 것
저장 쓰기가 늘어서 줄 단위 키와 채널별 상한으로 묶었어요. “채팅은 저장하지 않는다”던 이전 결정은 근거를 남기고 개정했어요.
결정 0016 · 0034

끊겨도 판은 서버 타이머대로, 같은 자리로 다시 연결

문제
iOS에서는 화면이 꺼지거나 다른 앱으로 가면 WebSocket이 끊어져요. 한 명 때문에 점심시간 10분짜리 판이 멈추면 안 돼요.
선택
참가할 때 토큰을 발급하고 다시 연결하면 같은 자리에 붙여 현재 상태를 다시 보내요. 진행은 기다리지 않고 서버 타이머대로 가요. 마감까지 못 보낸 투표는 무효표, 밤 행동은 행동 없음으로 처리해요.
다른 선택지
  • 끊기면 전원 일시정지: 공정하지만 짧은 게임에서는 한 명이 모두를 붙잡아요.
  • 끊기면 탈락: 모바일에서 흔한 끊김을 너무 가혹하게 벌해요.
결과
끊긴 사람은 테이블에서 흐릿하게 보이고, 돌아오면 이어서 해요.
감수한 것
자주 끊기는 사람은 불리해요. 대신 판의 길이는 항상 예측 가능해요.

풀었던 문제

문제 1 · 결정 0059

“이동할 때 핑이 튀는 것처럼 끊긴다”

증상
실기기(iPhone)로 해 보니 캐릭터를 탭한 뒤 잠깐 멈췄다가 움직였고, 걷는 도중 방향을 바꾸면 앞으로 튀었어요.
원인
서버 처리 시간은 0~1ms인데 한국에서 왕복이 약 155ms였어요(Cloudflare LAX 경유, 코드로 바꿀 수 없는 경로). 모든 캐릭터를 서버가 보낸 구간으로만 그려서, 탭하면 한 번 왕복하는 동안 서 있다가 응답이 오면 그만큼 앞으로 튀었어요.
해결
  • 내 캐릭터만 탭하는 즉시 서버와 같은 길찾기로 예측해서 걷기 시작해요.
  • 서버 구간이 오면 100~150ms에 걸쳐 위치 차이를 0으로 줄여요.
  • 서버가 요청을 거절하면 예측을 멈추고 서버가 아는 위치로 돌아와요.
  • 위치의 진실은 계속 서버예요. 속도 제한과 이동 가능 영역 검사도 서버가 해요.
배운 것
이전 UI 사양에 “예측 이동 금지”가 있었는데, 측정 결과를 근거로 그 결정을 개정했어요. 서버 권위를 지키면서 체감 지연만 줄이는 선을 정한 경험이에요.
문제 2 · 결정 0016 · 0062

알람이 늦거나 객체가 쉬었다 깨어날 때, 단계가 건너뛰어도 상태가 맞아야 한다

증상
단계(토론 → 지목 → 투표 → 밤 → 아침)는 알람으로 넘어가는데, 객체가 쉬었다 깨어나거나 알람이 늦으면 한 번에 여러 단계를 따라잡아야 해요. 중간 단계의 진입 처리가 빠지면 위치와 상태가 어긋나요.
해결
단계에 들어갈 때 일어나야 하는 상태 변화를 ON_ENTER 표 한 곳에만 두고, 알람 핸들러에서 직접 부르지 않기로 했어요. 알람이 여러 단계를 따라잡아도 중간 진입 처리가 순서대로 한 번씩 실행돼요.
더 찾은 것
코드 리뷰에서 “알람 따라잡기로 아침을 건너뛰면 밤에 옮겨 둔 위치가 되돌아가지 않는” 빈틈을 찾아 고쳤어요. 객체를 강제로 퇴거시킨 뒤 복원되는지 보는 테스트도 있어요.
문제 3 · 결정 0061

“받지 않았다”를 어떻게 증명하나

문제
정보가 새지 않았다는 건 “아무것도 오지 않았다”를 보여야 해서, 보통의 테스트로는 증명하기 어려워요.
해결
  • 메타모픽 테스트: 마피아의 행동만 다르게 한 두 판을 돌려서, 시민 편 소켓이 받은 프레임 열이 같은지 비교해요. 숨긴 정보가 한 글자라도 실렸다면 두 열이 달라져요.
  • 전 프레임 검사: 6명이 두 밤을 보내는 한 판의 모든 실제 프레임에서 서버 전용 키가 없는지 확인해요.
  • “오지 않았음”은 확인 신호(ping/pong)를 주고받은 시점까지 프레임이 없음을 보는 방식으로 증명해요.
결과
비공개 정보의 경계가 코드 리뷰 감이 아니라 테스트로 지켜져요. 새 기능을 더할 때도 같은 테스트가 회귀를 잡아요.

VERIFICATION

검증

규칙 테스트순수 규칙은 Node에서, 화면은 DOM 시뮬레이션에서, 방 서버는 실제 Workers 런타임(workerd) 안에서 실행해요.세 갈래로 나뉜 자동 테스트 5,000개 이상
정보 누설 검사밤 · 유령 · 채팅 · 동작 각각에 누설 테스트가 있어요. 위의 메타모픽 방식을 써요.
화면 E2E실제 Chrome으로 방을 만들고 여러 폰 화면 크기에서 배치 · 겹침 · 잘림 · 탭 크기를 좌표로 검사해요.이 검사가 밤 끝 알림이 360px 폭에서 버튼의 점을 1.8px 덮는 결함을 잡았어요
성능 게이트3D 맵과 캐릭터 8명을 CPU 4배 느리게 한 조건에서 5분 측정했어요.평균 60fps · 끊김 0 · 그리는 호출 최대 67 · 입장에서 조작까지 0.76초 · 실기기 iPhone 16 Pro 59.98fps

LIMITS & NEXT

한계와 다음 단계

응답 지연한국에서 서버까지 왕복이 약 155ms예요. 예측 이동으로 체감은 줄였지만, 요금제나 도메인 변경이 도움이 되는지는 확인하지 않았어요.
기기 범위성능은 최신 iPhone과 CPU 스로틀로 확인했어요. 저가 Android와 구형 iPhone은 실측하지 않았고, 느린 기기에서는 렌더 품질을 단계적으로 낮추는 사다리가 대신 지켜요.
부하방 단위로 객체가 분리돼 있어 방이 늘어도 서로 영향을 주지 않는 구조예요. 동시에 많은 방을 돌리는 부하 시험은 아직 하지 않았어요.
다음정식 출시 때 같은 웹 코드를 Capacitor로 감싸 Android · iOS 앱으로 내요. 링크로 참가하는 방식은 그대로 유지해요.
