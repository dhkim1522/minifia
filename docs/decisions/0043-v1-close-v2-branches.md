# 0043 v1.0 을 보관하고 v2.0 을 새로 기획한다. v1·v2 는 브랜치로 나눈다

- 상태: 채택
- 날짜: 2026-10-30

## 배경

- 1~5페이즈를 마친 v1.0 으로 팀 내 사람들과 실제 게임을 해 봤다. 사용자 판단: 이대로는 출시가 어렵다.
- 사용자: 지금까지의 작업을 버전 1로 두고, 버전 2로 새로 기획·설계·에셋 작업·고도화를 한다. 팀에서 받은 논의와 아이디어는 v2.0 을 시작할 때 하나씩 적고, 더하면 좋을 부분은 함께 논의한다.
- 사용자: 코드는 v1 위에 얹고, v1 과 v2 는 브랜치로 관리한다. v1 배포본은 그대로 두고 v2 는 따로 배포한다(권장안 승인).

## 결정

1. v1.0 마일스톤을 마감한다(`/gsd-complete-milestone`). 요구사항·로드맵·페이즈 문서·quick 작업은 `.planning/milestones/v1.0-*` 로 보관하고, git 태그 `v1.0` 을 붙인다.
2. 브랜치
   - `v1`: 태그 `v1.0` 에서 만든 유지 브랜치. v1 배포본(Worker `minifia`, https://minifia.dhplay.workers.dev)을 고칠 때만 쓴다. 새 기능은 넣지 않는다.
   - `v2`: v2.0 개발 브랜치. v1 코드 위에서 시작한다. 두 PC 모두 이 브랜치에서 작업하고 push 한다.
   - `main`: 지금 배포된 버전(현재 v1.0)을 가리킨다. v2 를 출시할 때 `v2` 를 `main` 에 합친다.
3. v2 개발 중 배포는 v1 과 다른 Worker 이름·주소에 한다(이름은 v2.0 기획에서 정한다). v1 주소는 그대로 유지한다. 서버와 화면은 함께 배포하고(결정 0036-15), 배포 전 계정 확인(결정 0042)은 v2 에도 그대로다.
4. 디자인 아티팩트(디자인 시스템·화면설계서·화면 흐름·캐릭터 에셋)와 포트폴리오는 지우지 않는다. v1.0 기준 기록으로 두고, v2 산출물은 새로 만들거나 새 페이지로 더한다.
5. 산출물 구분: 실행되는 것은 브랜치, 비교·참조하는 기록은 디렉토리로 나눈다(브랜치는 갈라져서 `v2` 에서 v1 기록을 바로 볼 수 없기 때문).
   - 브랜치: 앱 코드(`src`·`shared`·`worker`·`scripts`·`test`), 앱용 그림(`public/`).
   - 디렉토리: GSD 기록은 `.planning/milestones/v1.0-*`. 디자인 승인본은 v2 것을 `design/v2/` 에 새로 두고, 지금 `design/` 은 v1 기준으로 둔다(토큰 생성·그림 검사·갤러리 스크립트가 경로를 쓰므로 지금 옮기지 않는다. v2 디자인 승인 뒤 앱 기준을 `design/v2/` 로 바꾸고 v1 사본을 보관 위치로 옮긴다). 기획서·설계서는 v2 기획을 시작할 때 v1 본을 `docs/v1.0/` 으로 옮기고 v2 본을 새로 쓴다.
   - 한 디렉토리: 결정 기록 `docs/decisions/` 는 번호를 이어 쓴다.
   - git 밖: 사람용 아티팩트는 v2 를 새 아티팩트나 새 페이지로 더하고 v1 것은 보관한다.
6. v1 의 결정 기록(0001~0042)은 v2 에서도 유효하다. v2 에서 바꾸는 것은 새 번호의 결정으로 대체를 적는다(예: 결정 0008 의 "맵 이동 안 함", 결정 0038 의 "캐릭터 움직임 없음").

## 결과

- 다음 단계는 `v2` 브랜치에서 `/gsd-new-milestone` 으로 v2.0 을 시작하는 것이다: 팀 피드백 정리 → 기획 → 요구사항·로드맵 → 디자인 먼저 → 페이즈 구현.
- GSD 설정의 `git.branching_strategy` 는 `none` 그대로다. 브랜치는 위 규칙대로 사람이 관리한다.
